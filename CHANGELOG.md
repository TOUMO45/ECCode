# Changelog

## 0.3.5 — 2026-10-11 (TK-8 approval order for reviewed files)

### Gates and delivery (TK-8, found in the RescueStock pilot)
- **The defect.** `eccode audit` in `examples/rescuestock` failed with "src/services/requests.js modified after approval (phase:rework-1)", although the file's bytes were exactly the version `phase:d-extraction` approved later. `unreviewedChanges` (`lib/delivery.js`) built the latest approved version of each pinned file by walking `gateOrder`, where rework gates sit after every plan phase (`rework.opened` inserts them before the closing gates), so an older rework approval overwrote a newer phase approval of the same file. `deletedInReviewedWork` likewise counted a deletion as reviewed only when a phase gate *after the pinning gate in gate order* recorded it. Same root as TK-6 R2-3, which fixed the release-tree baseline with `approvalOrder`.
- **Its effect.** Audit, `reconcile`, the verification approval and `eccode deliver` judged a file against an outdated approval: a file a phase re-approved after a rework was reported as modified (the pilot's false failure, which blocks delivery), a file reverted to the rework's older bytes after the phase approved new ones would have passed unreported, and a file a phase deleted after a rework had pinned it was reported as "deleted after approval".
- **The fix.** `unreviewedChanges` reads the log once and walks the approved gates in approval order (`approvalOrder`: the event sequence of the review that approved each gate's current submission; `approvedAt`, then gate order, when the log lacks it), so the last approval to pin a file is its current version, and a deletion counts as reviewed when a phase approved after the pinning approval recorded it. The other `gateOrder` walks in `lib/` were checked and left: `tasks.submittedContent`, the architecture/design pin check in `gates.submit` and `recordsPins` ask whether *any* gate pins something (order-independent); `previousGate` (`lib/gates.js`) is the gate sequence itself; `lib/reconcile.js` collects every approved review's evidence; `lib/status.js`, `rework.js` (the verification gate's status) and the delivery report's gate table list or filter, they do not decide which approval is current; `preconditions` only requires every gate to be approved.
- **Records already written.** Nothing in the record format changes; the pilot's committed record (`b74b357`, 1156 events) replays to a byte-identical `state.json` under 0.3.4 and 0.3.5, and on a copy taken from git objects `eccode audit` now passes (0.3.4: "Audit FAILED: src/services/requests.js modified after approval (phase:rework-1)").
- **Tests.** `tests/approval-order-reviewed-files.test.js` (3, synthetic gate states over a real two-commit history with the approving reviews' sequence in the log and tied timestamps): a file approved by a rework and later by a phase with new bytes is current at the phase's version, and reverted to the rework's bytes is reported against the phase; the reverse order (phase first, rework later); a deletion recorded by a phase approved after the rework is reviewed, one recorded by a phase approved before it is not. The first and third failed on 0.3.4 with the pilot's message; the second passed (a regression guard).

## 0.3.4 — 2026-10-11 (TK-6 nested-project tree digest)

### Gates and evidence (TK-6, found by a reviewer of the RescueStock pilot)
- **The defect.** `treeDigest(root)` (`lib/project.js`) is the content digest command evidence records as `tree` and every gate submission records beside its `commit`; completion and phase/verification review refuse a cited check whose `tree` differs from the current one ("ran on different bytes"). It re-hashes the files git reports as dirty with `git hash-object --stdin-paths`, and it passed their paths relative to the project root while running in the project directory. `--stdin-paths` resolves its input from the repository's top level, not the working directory, so for a project nested below the repository root (`examples/rescuestock`) it read the wrong path. Reproduced from `examples/rescuestock`: `printf 'src/main.js\n' | git hash-object --stdin-paths` fails with "could not open 'src/main.js'", and `printf '.eccode/state.json\n' | git hash-object --stdin-paths` hashes the repository root's `.eccode/state.json` instead of the project's.
- **Its effect on tree pinning (R28).** (a) Whenever a dirty file of the nested project (modified or untracked) had no file at the same relative path under the repository root, the whole batch failed and the digest was null: the evidence run was recorded without `tree`, and the completion and review stale checks compared nothing, so tree pinning was silently off. The project's own `.eccode/` files were in the hashed batch although the digest excludes them, so a draft under `.eccode/drafts/` alone was enough. (b) When a same-named file existed at the repository root (`package.json`, `.eccode/*`), the digest covered that file's bytes instead of the project's: a later edit of the project's file did not change the digest (a stale check passed as current), and an edit of the root twin did (a current check was refused as stale). In the pilot's committed record (`220d3fa`) 327 of the 448 command runs carry no `tree`.
- **Its effect on the release-tree check (R30).** `gate submit` recorded the `commit` only together with a digest, so a null digest dropped the commit too (and `eccode deliver` dropped the release commit the same way). All 19 gate submissions in the pilot's committed record carry no commit, and the release-tree diff (`releaseTreeChanges`), which starts at the first approved submission's commit, skipped such records as an older engine's: for every gate the pilot has approved, nothing compared the release tree with a reviewed commit.
- **The fix.** The dirty paths are prefixed with `git rev-parse --show-prefix` (repository paths) and `hash-object --stdin-paths` runs from `git rev-parse --show-toplevel`, so it reads the project's own bytes and applies `.gitattributes` by each file's repository path; dirty paths under the project's `.eccode/` are no longer hashed at all, since the digest leaves them out. Both `rev-parse` paths lose exactly git's trailing newline instead of being trimmed (a repository directory ending in a space hashed the files of its trimmed sibling; a project under a directory starting with a space ignored its own dirty files; `workingTreeStatus` in `lib/delivery.js` trimmed the prefix the same way), and every `--stdin-paths` line is C-quoted (a name with a newline or a trailing CR, or starting with `"`, nulled the digest or hashed another name, at the repository root too). A project at the repository root gets the same digest as on 0.3.3 wherever 0.3.3 computed it correctly.
- **"Inside git" is a work tree, not a HEAD that resolves** (review R2-1). `treeDigest` and `treePin` ask `git rev-parse --is-inside-work-tree`; the digest needs no HEAD, so on a fresh repository before its first commit, or after `git checkout --orphan`, it is computed (oracle-equal, and it moves on an edit) and a run there is pinned. Earlier rounds of 0.3.4 read an unborn HEAD as "outside git": the run carried no tree and no marker, nothing was printed, and a run recorded on an orphan branch, then cited after switching back and editing, was accepted as if it had run on the new bytes. `gate submit` inside a work tree whose HEAD does not resolve is refused (`NO_COMMIT`: make the first commit, or switch back to a branch with commits) rather than marked: that way no approval made on 0.3.4 inside a work tree lacks a commit, release-baseline gaps can only come from older records, and the remedy is one commit. `eccode deliver` is refused in the same state.
- **The engine's git ignores the caller's repository selection** (review R3-1). Every git call the engine makes (`lib/project.js` `git`, `lib/delivery.js` `gitOut`, the only two) runs with every `GIT_*` variable removed, not a list (review R4-4: git grows new ones, such as `GIT_ATTR_SOURCE`; the engine's calls are local and read-only and need none, so `GIT_TERMINAL_PROMPT` and the like go too, harmlessly), among them `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_COMMON_DIR`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_CEILING_DIRECTORIES`, `GIT_DISCOVERY_ACROSS_FILESYSTEM`, `GIT_NAMESPACE` and every `GIT_CONFIG*` (`lib/project.js` `gitEnv`; `lib/project.js` `gitEnv`), so discovery always starts from the project directory. Before, `GIT_DIR=<elsewhere>` (or `GIT_WORK_TREE`, `GIT_CEILING_DIRECTORIES`, a `GIT_CONFIG_*` override) on an eccode command made the engine see no work tree: the run recorded neither tree nor marker and printed nothing, a stale run was cited as current, `gate submit` recorded an approval with no commit, and completion's ownership accounting, delivery's clean-tree check and the release-tree diff were skipped; an eccode call from a git hook (which sets `GIT_DIR` and `GIT_INDEX_FILE`) misfired the same way for a nested project. With this, "inside a work tree" in the bullets above means the work tree discovered from the project directory, whatever the caller's environment says. A deliberate consequence (review R4-3): a repository reachable only through `GIT_DIR`/`GIT_WORK_TREE` (a bare repository driving a separate work tree, as some dotfile managers and CI layouts do) is outside git for the engine; `.git` files, linked worktrees and `--separate-git-dir` are found from the project directory and are unaffected.
- **The guard refuses the common inline environment overrides on a CLI call, and only there** (reviews R3-1, R4-1, R4-2, R5-1). `GIT_*`, `NODE_OPTIONS` (which can preload code into the CLI), `PATH`, `HOME` and `XDG_CONFIG_HOME` assigned to an eccode CLI invocation are refused, as is `env -i` running it, in these forms: in the call's own prefix, after `env`, inside `env -S '…'`, `bash -c '…'`, `eval` or the command an `evidence run` runs, or assigned or exported earlier in the same command line (`export PATH=…; eccode …`, `declare -x …`, `GIT_DIR=x; eccode …`). Only real `NAME=value` assignments count: bare names, words inside quoted arguments, commit messages, heredoc bodies and `grep` patterns, and assignments to other commands (`GIT_AUTHOR_DATE=… git commit -m "eccode …"`, `GIT_PAGER=cat git log`, `NODE_OPTIONS=… npm test`, `PATH=… make`) are not. The first version of this rule matched any word on any line that mentioned `eccode` and refused the orchestrator's own commit messages and a reviewer's `grep -n GIT_DIR bin/eccode.js`. One earlier allowance is withdrawn on purpose: `export PATH="$PWD/node_modules/.bin:$PATH"; eccode evidence run … -- npm test` is refused; put the assignment inside the checked command (`eccode evidence run … -- 'PATH="$PWD/node_modules/.bin:$PATH" npm test'`). The guard reads commands and does not close the inline route: a brace group (`{ PATH=…; eccode …; }`), a variable set by `read`, `printf -v` or a sourced file before the CLI, a quoted `"<<EOF"` hiding the following lines from this check, and `node -r`/`--require`/`--import`/`--loader` preloads still pass. They are residual 1 (threat model residual 16), and none defeats the engine's own refusal of a failing git (below); what they reach is a git or a preload that lies.
- **A failing git no longer turns pinning off** (review R4-2). Once the record pins (some run carries a tree or the marker, or some submission a commit), "not a work tree" is a failing git (a broken `git` first on `PATH`, a moved project), not a project that left git: `evidence run` records `treeUnavailable` with the CLI warning, `gate submit` is refused (`NO_COMMIT`), and delivery is refused. Completion and review refuse to cite a run that carries a tree (or the marker) while the current digest cannot be computed ("cannot verify that the cited check(s) … ran on the current tree"); before, the stale check was skipped and a run was accepted on bytes it never saw. The engine trusts the `git` it finds on `PATH`: a git that lies is residual 1 (threat model residual 16). Known follow-ups, recorded there: before a record pins anything a failing git still reads as no git (telling spawn `ENOENT` from a non-zero `git --version` would close it; R5-2), and the guard's case-insensitive names refuse `env path=/x eccode …` on Linux (R5-3, a harmless over-denial).
- **A digest that is still unavailable is no longer silent** (review F2 of the first repair; R2-4, R2-6). Inside a work tree, when the digest cannot be computed, `evidence run`, `gate submit` and `eccode deliver` record `treeUnavailable: true` and the CLI prints a warning on stderr ("tree pinning is off for this run/submission/release"); a submission and a delivery keep their commit whatever the digest (`lib/project.js` `treePin`; the release commit used to be dropped silently with the digest). `eccode audit` counts the marked runs ("Command runs recorded with tree pinning off", `treeUnavailableRuns` in `--json`). Completion and review refuse to cite a run marked `treeUnavailable` while the current digest is available ("ran while the source tree digest was unavailable … run the check again"), which is small and safe because only runs recorded on 0.3.4 carry the marker. Outside a work tree nothing is recorded, as before, and records without the marker replay unchanged. Refusing `gate submit` when the digest (not HEAD) is unavailable is not done (threat model residual 16).
- **Commit-less approvals are reported, not skipped** (review F1, R2-2, R2-3). When the record shows the engine pins trees (some run carries a tree or the marker, or some submission a commit) and the project is in a work tree, `unreviewedChanges` reports every approval made before the first approved commit whose submission recorded none as a release-baseline gap (`unpinned: true`). "Before" and "first" are in approval order, the event sequence of the review that approved each gate (falling back to `approvedAt`, then gate order, for a state without its log): rework gates sit after every plan phase in gate order, so a rework approved with a commit before a later phase was not the baseline, and commit-less reworks approved before it were not named. The gap states what the record shows, that no commit was recorded, and lists the possible causes (outside a work tree or HEAD unborn at submission; an engine older than 0.3.0; 0.3.0–0.3.3 dropping it with an unavailable digest, TK-6) instead of asserting TK-6. It is a warning: `eccode audit` lists it under "Release-tree baseline gaps (warnings)" and still passes, `reconcile` reports it as a `release-baseline` warning, and neither the verification approval nor `eccode deliver` is refused for it, since no later submission can repin a past approval. The delivery report no longer claims that every file is older than the first reviewed submission or pinned: with gaps, its release sentence claims only the changes since the first approved commit, names the commit-less gates with the possible causes, and repeats them under limitations (`releaseBaselineGaps` in the JSON handoff).
- **Records already written are unchanged.** A run recorded without `tree` stays unpinned (the stale check skips it, as for records older than 0.3.0); a run whose recorded `tree` was computed over a root twin no longer matches the corrected digest and is refused as stale when cited: re-run the check. For the pilot, the release-tree baseline becomes the first submission recorded on 0.3.4 to be approved: a file changed before that commit and pinned by no approval is not reported, and every commit-less approval before it, reworks included, appears as a baseline gap. The reducer copies the new fields only when an event carries them, so every shipped record replays to the same snapshot. Threat model residual 16 lists this, the bytes the digest does not see (assume-unchanged and skip-worktree files, a project in an ignored directory, submodules, edited symbolic links, names that are not valid UTF-8) and what is not done.

## 0.3.3 — 2026-10-09 (Windows lock and rename retries, TK-3; cause confirmed only by the Windows job)

### Locking and atomic writes (TK-3, open: two candidate causes, decided by the next captured stderr)
- **The symptom.** The gating `toolkit (windows, node 22)` job failed four of the last ~25 runs of the pilot branch (runs 66, 67, 68 and 92; Linux and macOS passed every time), each time on one of the two tests that spawn six `risk add` CLI processes against one record (`tests/resume-delivery.test.js` "concurrent writers never corrupt the log"; run 66 on `tests/review-F7.test.js` "F7 two concurrent writers …"): one child exited 1 (`[0, 1, 0, 0, 0, 0]`) and its stderr was not captured. Exit 1 is the CLI's `internal error` branch (`bin/eccode.js`): a raw `fs` error escaped the engine, not an `EccodeError` (exit 2). Two races in the tree produce exactly that on Windows, and nothing recorded says which one fired; both are repaired below, neither is confirmed, and **TK-3 stays open until a Windows run captures the error** (both spawn tests now keep the children's stdout and stderr and print them with the exit codes on failure: `tests/helpers.js` `spawnCli`, `assertAllExitZero`). The independent review of the first repair (`docs/evidence/verification-0.3.0/lock-tk3-review/REVIEW.md`, read against libuv's `win/fs.c` and `win/error.c`) rates the rename race the likelier of the two.
- **Candidate 1, the rename over `state.json` (review F1, rated likelier).** Every `risk add` reads `state.json` and `events.jsonl` *outside* the record lock (`lib/authority.js` `commitReserved` previews the state before the lock) while the writer inside the lock renames a temp file over `state.json` (`lib/store.js` `commit` → `lib/util.js` `writeFileAtomic`). libuv implements that rename as `MoveFileEx(MOVEFILE_REPLACE_EXISTING)` without POSIX semantics, which Windows refuses with `ERROR_ACCESS_DENIED` → `EPERM` while any process holds the target open: six children racing readers against one renamer fits one failure in six. `writeFileAtomic` now retries the rename on `EPERM`, `EACCES` and `EBUSY` at 25 ms for a bounded 1.5 s (`retryMs`), removes its temp file when it gives up or meets any other error, and throws the error as it came. Regression: `tests/write-atomic-retry.test.js` (five cases on a mocked `fs.renameSync`: `EPERM` twice then success, `EACCES` and `EBUSY` once, refused past the bound, `ENOSPC` at once; all five failed before the change, `ENOSPC` only on the temp file it left behind). A follow-up may also move the preview read under the lock.
- **Candidate 2, the lock file itself.** `withLock` (`lib/util.js`) opened the lock file with `wx` and threw anything but `EEXIST`. On Windows a lock file a scanner or indexer holds without share flags answers `EBUSY`, and a name whose delete is pending answers `EPERM`; the review notes that libuv's unlink uses POSIX delete semantics on the runner's OS, so the holder's own release rarely leaves such a window and this needs an external handle. `EPERM`, `EACCES` and `EBUSY` from the open are now contention like `EEXIST`; a `stat` or `unlink` the platform refuses on the staleness path, and a stale lock just broken, both reach the timeout check and poll at 25 ms instead of retrying at once (the old `continue` could spin without reaching the timeout; review F3); the holder retries a refused release up to ten times so a lock left behind no longer holds every writer until `staleMs`; a write refused on the freshly opened lock closes the fd and removes the file before rethrowing instead of polling on our own lock (review F4). Everything is bounded by the same `timeoutMs`, every other code is still thrown at once, and because on POSIX `EPERM`/`EACCES` on the lock file is a permission problem rather than contention, `LOCK_TIMEOUT` now names the last error it met in its message and `details.lastError` (review F2). Regression: `tests/lock-transient-errors.test.js` (twelve cases on a mocked `fs`; seven of the first eight failed on 0.3.2, the F2/F3/F4 cases failed on the first repair).
- **Known, unchanged (review F5):** the release deletes whatever file is at the lock path, so a holder that outlived `staleMs` and was broken by another process removes the breaker's lock on its way out, as in every earlier version; verifying the lock's pid before unlinking is a future hardening.

### CLI
- **`sleepSync` is exported by `lib/util.js`** (review F8, found in passing). `bin/eccode.js` imported it for the `EAGAIN` retry of its terminal line reader, where a non-blocking TTY would have met a `TypeError` instead of a retry. `tests/lock-transient-errors.test.js` checks every name the CLI destructures from `lib/util` is exported.

## 0.3.1 — 2026-10-09 (verification checkpoint)

An independent adversarial verification of 0.3.0 (`docs/evidence/verification-0.3.0/REPORT.md`: a fresh agent context, probes per finding with variations, run on `5da8913`'s engine) found that F1, F2 and F4 were **not closed**: three new blocking bypasses, six non-blocking ones, no overblocking. The RescueStock pilot found a fourth defect in the guard. Every repair below was written failing-test-first on a separate branch and independently reviewed before merging; the lead's matrix is `docs/build/eccode-verification.md`. This is the version the pilot runs on.

### Gates and evidence (F1, F2, F3)
- **Required criteria come from the pinned bytes, not the file on disk** (NEW-1, blocking): design and verification derive their required criteria from the approved brief; if that file no longer matches the hash the architecture approval pinned, `gate show`, both review decisions and a later submission that lists the file are refused with `APPROVED_ARTIFACT_CHANGED` (restore it from git; a revision is a new artifact of a later submission). Before: a document author could rewrite the brief after approval, drop criteria, and verification re-pinned the edited file with `audit` reporting "approved artifacts unchanged".
- **The release tree is compared from the first approved commit** (NEW-3, blocking): `unreviewedChanges`/`releaseTreeChanges` diff from the earliest approved submission's commit, and a verification approval is refused while any change is not pinned by that very submission at its current hash. Before: a file committed between a phase approval and the verification submission, listed by no gate, dropped out of the check once verification was approved and shipped in the release commit.
- **A brief with no criteria ids cannot be approved** (NEW-2): when the configured criteria sections list no ids, the architecture and verification approvals are refused with the resubmit instruction; `review.criteriaSections.architecture: []` turns the rule off explicitly.
- **A staged rename declares its old path** (NEW-4): completion accounting runs `git diff --no-renames`, so `git mv old new` with only `new` declared is refused; the release report still names `from`.
- **The declared check is bound to its working directory** (NEW-5): plans may declare `verification.cwd` (relative, inside the project); completion and phase approval require the cited run's recorded cwd to equal it (default: the project root).

### The guard (F4, F5, F6; pilot), restructured on real paths
The guard repairs went through five independent review rounds (`docs/evidence/verification-0.3.0/guard-repairs-review/REVIEW.md`): the first two attempts fixed the reported cases with patterns and the reviewer found a new bypass each time (a record planted inside the record, then a record **alias** made with allowed commands). The third attempt changed the structure instead, and two further rounds closed the link cases. What ships:
- **Every write target is judged on its real path, for every context including the main session**: Edit/Write targets and every shell writer the guard reads (redirects including `>|`, `tee`, `cp`/`mv`/`rm`/`rmdir`/`ln`/`install`/`rsync`, `sed -i`, `dd`, `find -delete`/`-exec`, `tar -x -C`, `unzip -d`) are resolved from the hook cwd through existing links, dangling links included, and judged on both the lexical and the real path. **Everything under a record directory except the three draft areas is the record** (`.eccode/drafts`, `.eccode/artifacts`, `.eccode/reviews/drafts`), replacing the enumerated file list. `xargs` feeding a writer while the line names a record is refused.
- **Nested projects are judged by their own record** (pilot): the project root is the nearest real, non-link `.eccode/` above the target that holds `events.jsonl` and lies in no other record; `init` refuses a root inside a record. Before, a project at `examples/<app>/` inside a repository with its own record was judged by the outer record, so its reviewers and authors could not write their own draft and artifact areas (two pilot dispatches failed this way).
- **A link created and written through in the same command line is refused** when the line names a record, an operand of the link is computed, or an operand already resolves into a record through existing links (`ln -s "$PWD/.eccode" lk && echo x > lk/state.json`; `a -> .eccode` then `ln -s a b && …`). Record-free build lines (`ln -sf ../lib/cli.js bin/cli && echo built > .build-stamp`) pass.
- **`>|` is a redirect** (NEW-6, blocking): the clobber operator was split at its bar, so `echo x >| file` had no target and every role could write any file.
- **The CLI is recognised on tokenized words at every depth** (`ecc"ode".js`, `$'eccode'`, `eccode.js${X}` bind their `--actor`; a comment naming the CLI no longer counts); **a shell function or alias wrapped around the CLI is refused** (NEW-7) in every bash form (`function e`, `e() (…)`, `e() if … fi`, after `then`, inside `{ }`, `bash -c`, `sh -c`, `evidence run -- '…'`), with any name bash accepts.
- **`ECCODE_SHARED_MEMORY`, `ECCODE_ROOT`, `ECCODE_SEQUENTIAL_ROLES` and `ECCODE_HOOKS` may not be set inline** (NEW-9), like `ECCODE_ACTOR/TEST/NOW` before them; an assignment with a **computed name** (`export $V=…`, `declare "$N"=…`, `printf -v "$N"`, `declare -n`) in the same line as the CLI is refused, while literal names with computed values (`export OUT="$HOME/x"`) pass.
- From the Windows CI run of 0.3.0 (2 of 233 failed): record and memory patterns accept both path separators and are applied to the raw command before tokenizing; the CLI is recognised by a quoted Windows path. The tokenizer keeps bash semantics on every platform (a first version that kept backslashes was rejected in review: `.eccode/drafts/.\./state.json` read as a draft while bash writes the record). Windows itself is still not run here.

### Documented, not repaired (threat model §4)
- Metadata outside a shared record's attested hash (reviewer name, evidence snapshot status) is unbound (NEW-8).
- Known-shape shell writes the guard does not read as writes (`rm`, `git apply`, `patch`, `curl -o`, `tar -x`, a symlink that lives outside the project): residual 1.
- The final handoff's sentence that user events "were confirmed by a person at a terminal" is qualified: an event forged offline with a valid hash passes `audit` (residual 3).
- The npm tarball ships `docs/evidence/` (8 MB); hygiene, not a defect.
- Guard residuals confirmed by the reviews: a hard link to a record file shares its inode and cannot be told from the file; `>"|"` is read as the clobber operator although bash writes a file named `|` (over-denial); a computed, record-free link operand beside another write is refused (over-denial); `mklink` is not a bash command and contributes no target; a role's `mv` of a project file into its draft area is refused for the source, with a message that names the target.

### Gates and evidence (F1, F3)
- **An approval must cover the criteria the gate requires** (`gates.requiredCriteria`, printed by `eccode gate show <gate>`): the brief's acceptance-criteria ids (list items or table rows under `review.criteriaSections`, default `['Acceptance Criteria']`) for architecture, design and verification; `phase:<id>` for the plan; `task:<id>` and `phase:<id>` for a phase. Missing ids are refused in one message; duplicate ids, and ids that look required but are not (`task:nope`, `AC9` beside AC1–AC8), are refused; free-form ids (`C1`, `security`, `lessons`) stay allowed. `templates/review.json` and the reviewer prompts say so.
- **Anchors must exist:** `artifact:<path>#<anchor>` in a review is validated: a Markdown heading (text or GitHub slug), a JSON dot path (`tasks.api`, `phases.0.id`) or a line range (`L10`, `L10-L20`).
- **Checks are bound to what they prove.** Command evidence records `tree` (a digest of the source tree's content: the git blob id of every file's working bytes outside `.eccode/`, independent of HEAD, the index and status codes) and `logFileSha256` (the bytes written to the log). Completing a task that declares a verification command needs a passing run of that command by the owner after the claim (whitespace-insensitive, compared after redaction); method-only tasks keep the any-passing-check rule; a cited check whose tree differs from the tree being handed off is refused ("ran on different bytes, re-run it"). Phase approvals must cite a reviewer run of every verification command the phase's tasks declare, and cited reviewer checks whose tree differs from the tree under review are refused (verification gates too).
- **Evidence logs are integrity-checked when cited:** a command evidence whose log was deleted or altered no longer resolves (handoff, completion, review); older records are checked against the output digest with the header stripped; `eccode reconcile` and `resume` report missing or altered logs that done tasks or approvals relied on as blocking `evidence-tampered` issues.

### The release tree and the release policy (F2, F5)
- `task claim` refuses `DIRTY_OWNERSHIP` when files inside the task's ownership are already changed before the claim (commit or revert them), unless a gate submission pins exactly that content (a rejected attempt kept for the retry, an approved rework's uncommitted fix).
- Every `gate.submitted` records the `commit` and the tree digest; `delivery.completed` records the release commit and tree, and the final handoff states the release commit.
- `unreviewedChanges` (audit, reconcile, delivery) also reports every file git shows changed since the last approved submission's commit that no approved review pinned: added, modified, deleted or renamed after approval, untracked included; work in flight of open phases and deletions recorded by an approved task are excluded; `release.ignore` names generated paths; a submission whose commit is unknown is a blocker.
- `eccode deliver` refuses a dirty working tree outside `.eccode/` and `release.ignore`, and refuses while any risk of a severity in `release.blockRiskSeverities` (default `critical`, `high`) is `open`; the message names the mitigation command and the user-only acceptance command. The handoff lists accepted risks with who accepted them and when.

### The human channel (F5)
- `--actor user` is confirmed at a terminal: the CLI prints what is about to be recorded and waits for a person to type `yes`; without a TTY (a pipe, a script, an agent's shell tool) it is refused before anything is recorded (`USER_AUTH_REQUIRED`). `ECCODE_TEST=1` is the test suite's switch and is never set in an agent's environment; the guard denies setting it inline.
- The guard denies `--actor user` from every agent context, the main session included (and an exported `ECCODE_ACTOR=user`), pointing at the two ways forward.
- **Bounded delegation,** recorded in the hash-chained log: `eccode delegate grant --actor user --to orchestrator --action <gate.reopen|task.reset|rework.open|risk.accept|rebuild.force|improve.adopt|decision.record> [--target <id>] [--uses N] [--expires <minutes>] --reason …` (defaults 1 use, 4 hours; `delegate list`, `delegate revoke`). The orchestrator reruns the refused command with `--delegation <id>`: the use is spent first (`delegation.used`), the action's event carries `onBehalfOf: user` and the delegation id, and the handoff lists it under "User decisions". Exhausted, expired, revoked, another role's or another action's delegations are refused and spend nothing; a refused action spends nothing. A rework past `limits.maxReworks` is now `USER_AUTH_REQUIRED` (was `REWORK_LIMIT`). `decision add --on-behalf-of user` records a decision as the user's only under a delegation.

### The guard (F4)
- Shell writes get the same answer as the Edit tool for every ECCode role: redirects, `tee`, `cp`/`mv`/`ln`/`install`/`rsync`, `sed`/`perl -i`, `dd` and `touch` by reviewers and document authors are denied outside their draft areas; the former blanket allowance of `.eccode/` shell targets is gone.
- Inline interpreter programs that call a file-writing API (`node -e`, `python -c`, `perl`/`ruby -e`, `php -r`, `deno eval`, heredocs and pipes into a bare interpreter; wrappers such as `env`, `exec`, `nohup`, `timeout`, `npx` looked through) are denied for every ECCode role with a hint to use the Edit tool or a script under the draft area. Relative targets resolve from the hook cwd; a write after a `cd` inside the command is denied because it cannot be bound.
- Edit/Write targets outside the project that are record or memory files (another project's `.eccode/`, `~/.eccode/memory/`) are denied for every context.

### Shared memory attestation (F6)
- `memory promote` binds the shared copy to the review that verified it: the record carries an `attestation` (sha256 of layer, status, trust and content as saved; the verifying review's revision, reviewer, time and content hash from the project log; promoter, time, engine version), and the shared store gains an append-only, hash-chained `attestations.jsonl`. Retrieval recomputes the hash and requires the index to agree; a shared record whose content, status, trust or layer changed, whose index line is missing or chain is broken, or which an older engine promoted is **quarantined**: `memory check` returns `provisional` with the reason, search weights it as unverified and flags the row, `memory show` prints the attestation, and the new `eccode memory audit [--scope shared|project|all]` lists every broken record (exit 2). Shared records are immutable (`revise`, `review`, `supersede` refuse them); a corrected lesson is re-verified in its project and promoted again, which supersedes the old copy through the engine.

### The store (F7)
- Every event carries `stateHash`, the digest of the state it produced, inside the hash chain. `Store.state()` returns the snapshot only when it matches that digest (or, for records written before the digest existed, a full replay) and refuses a snapshot whose content differs from the log with `SNAPSHOT_DIVERGED` before anything is appended; the message names the first differing field, `eccode audit` shows it and `eccode rebuild --actor orchestrator` rewrites the snapshot. A torn `state.json` is rebuilt from the log. `eccode audit` gains `warnings` for a task completed whose handoff was never recorded (a crash between the two commits); `eccode handoff record` fills the gap.

### Limits (F8)
- `limits.maxActiveRuns` (default 4): `run start` refuses `RUN_LIMIT` when that many runs are open. `limits.reserveUsdPerRun` (default off) holds budget back for runs in flight. Usage the engine was never given is recorded as unknown, never as `$0`: `run end --no-usage` records `null`, `recover` closes interrupted runs with the real elapsed time and unknown usage, tokens without a dollar figure and without pricing leave the cost unknown. Totals are a lower bound; `status`/`resume` say so and name the runs to fill in with `run correct`. `docs/usage.md` "Limits: what the engine enforces and what it only accounts" states which limits are enforced, which are self-reported and which only the host can enforce.

### Portability and release (F9)
- The review's five Windows failures were in the test suite, not the engine: fixtures needing `sh`, `grep`, `true`/`false` or `;` (absent on `cmd.exe`), POSIX-only quoting of `evidence run -- …` arguments, and test repositories whose checkouts rewrote LF as CRLF under a global `core.autocrlf=true`. `shellQuote` lives in `lib/util.js` (one copy) with a `win32` branch; fixtures are portable `node -e` programs and a static scan keeps them so; `tests/helpers.js initRepo()` creates every throwaway repository with `core.autocrlf=false`; `.gitattributes` keeps every text file LF on every platform and exempts the review-bundle logs and evidence logs. Windows itself was not run from this session: the fixes follow the analysis of the reviewer's log and are unverified until the CI job passes.
- `lib/index.js` is the package entry point; `npm run validate` checks `main`, every `files` entry, the plugin manifest versions and that `npm pack` ships the engine. Supported platforms declared (Linux and macOS with Node 18.17/20/22 gated by CI; Windows reported). An upgrade/rollback test installs the 0.1.0 toolkit, writes a record, installs the current toolkit over it, audits, and rolls back.
