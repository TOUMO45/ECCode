Several rules are stricter than 0.2.0; the record format is compatible (old logs replay unchanged; see "Record compatibility" in `docs/architecture.md`).

### Gates and evidence (F1, F3)
- **An approval must cover the criteria the gate requires** (`gates.requiredCriteria`, printed by `eccode gate show <gate>`): the brief's acceptance-criteria ids (list items or table rows under `review.criteriaSections`, default `['Acceptance Criteria']`) for architecture, design and verification; `phase:<id>` for the plan; `task:<id>` and `phase:<id>` for a phase. Missing ids are refused in one message; duplicate ids, and ids that look required but are not (`task:nope`, `AC9` beside AC1–AC8), are refused; free-form ids (`C1`, `security`, `lessons`) stay allowed. `templates/review.json` and the reviewer prompts say so.
- **Anchors must exist:** `artifact:<path>#<anchor>` in a review is validated: a Markdown heading (text or GitHub slug), a JSON dot path (`tasks.api`, `phases.0.id`) or a line range (`L10`, `L10-L20`).
- **Checks are bound to what they prove.** Command evidence records `tree` (a digest of the source tree's content: the git blob id of every file's working bytes outside `.eccode/`, independent of HEAD, the index and status codes) and `logFileSha256` (the bytes written to the log). Completing a task that declares a verification command needs a passing run of that command by the owner after the claim (whitespace-insensitive, compared after redaction); method-only tasks keep the any-passing-check rule; a cited check whose tree differs from the tree being handed off is refused ("ran on different bytes, re-run it"). Phase approvals must cite a reviewer run of every verification command the phase's tasks declare, and cited reviewer checks whose tree differs from the tree under review are refused (verification gates too).
- **Evidence logs are integrity-checked when cited:** a command evidence whose log was deleted or altered no longer resolves (handoff, completion, review); older records are checked against the output digest with the header stripped; `eccode reconcile` and `resume` report missing or altered logs that done tasks or approvals relied on as blocking `evidence-tampered` issues.

### The release tree and the release policy (F2, F5)
- `task claim` refuses `DIRTY_OWNERSHIP` when files inside the task's ownership are already changed before the claim (commit or revert them), unless a gate submission pins exactly that content (a rejected attempt kept for the retry, an approved rework's uncommitted fix).
- Every `gate.submitted` records the `commit` and the tree digest; `delivery.completed` records the release commit and tree, and the final handoff states the release commit.
- `unreviewedChanges` (audit, reconcile, delivery) also reports every file git shows changed since the last approved submission's commit that no approved review pinned: added, modified, deleted or renamed after approval, untracked included; work in flight of open phases and deletions recorded by an approved task are excluded; `release.ignore` names generated paths; a submission whose commit is unknown is a blocker.
- `eccode deliver` refuses a dirty working tree outside `.eccode/` and `release.ignore`, and refuses while any risk of a severity in `release.blockRiskSeverities` (default `critical`, `high`) is `open`; the message names the mitigation command and the user-only acceptance command. The handoff lists accepted risks with who accepted them and when.

### The human channel (F5)
- `--actor user` is confirmed at a terminal: the CLI prints what is about to be recorded and waits for a person to type `yes`; without a TTY (a pipe, a script, an agent's shell tool) it is refused before anything is recorded (`USER_AUTH_REQUIRED`). `ECCODE_TEST=1` is the test suite's switch and is never set in an agent's environment; the guard denies setting it inline.
- The guard denies `--actor user` from every agent context, the main session included (and an exported `ECCODE_ACTOR=user`), pointing at the two ways forward.
- **Bounded delegation,** recorded in the hash-chained log: `eccode delegate grant --actor user --to orchestrator --action <gate.reopen|task.reset|rework.open|risk.accept|rebuild.force|improve.adopt|decision.record> [--target <id>] [--uses N] [--expires <minutes>] --reason …` (defaults 1 use, 4 hours; `delegate list`, `delegate revoke`). The orchestrator reruns the refused command with `--delegation <id>`: the use is spent first (`delegation.used`), the action's event carries `onBehalfOf: user` and the delegation id, and the handoff lists it under "User decisions". Exhausted, expired, revoked, another role's or another action's delegations are refused and spend nothing; a refused action spends nothing. A rework past `limits.maxReworks` is now `USER_AUTH_REQUIRED` (was `REWORK_LIMIT`). `decision add --on-behalf-of user` records a decision as the user's only under a delegation.

### The guard (F4)
- Shell writes get the same answer as the Edit tool for every ECCode role: redirects, `tee`, `cp`/`mv`/`ln`/`install`/`rsync`, `sed`/`perl -i`, `dd` and `touch` by reviewers and document authors are denied outside their draft areas; the former blanket allowance of `.eccode/` shell targets is gone.
- Inline interpreter programs that call a file-writing API (`node -e`, `python -c`, `perl`/`ruby -e`, `php -r`, `deno eval`, heredocs and pipes into a bare interpreter; wrappers such as `env`, `exec`, `nohup`, `timeout`, `npx` looked through) are denied for every ECCode role with a hint to use the Edit tool or a script under the draft area. Relative targets resolve from the hook cwd; a write after a `cd` inside the command is denied because it cannot be bound.
- Edit/Write targets outside the project that are record or memory files (another project's `.eccode/`, `~/.eccode/memory/`) are denied for every context.

### Shared memory attestation (F6)
- `memory promote` binds the shared copy to the review that verified it: the record carries an `attestation` (sha256 of layer, status, trust and content as saved; the verifying review's revision, reviewer, time and content hash from the project log; promoter, time, engine version), and the shared store gains an append-only, hash-chained `attestations.jsonl`. Retrieval recomputes the hash and requires the index to agree; a shared record whose content, status, trust or layer changed, whose index line is missing or chain is broken, or which an older engine promoted is **quarantined**: `memory check` returns `provisional` with the reason, search weights it as unverified and flags the row, `memory show` prints the attestation, and the new `eccode memory audit [--scope shared|project|all]` lists every broken record (exit 2). Shared records are immutable (`revise`, `review`, `supersede` refuse them); a corrected lesson is re-verified in its project and promoted again, which supersedes the old copy through the engine.

### The store (F7)
- Every event carries `stateHash`, the digest of the state it produced, inside the hash chain. `Store.state()` returns the snapshot only when it matches that digest (or, for records written before the digest existed, a full replay) and refuses a snapshot whose content differs from the log with `SNAPSHOT_DIVERGED` before anything is appended; the message names the first differing field, `eccode audit` shows it and `eccode rebuild --actor orchestrator` rewrites the snapshot. A torn `state.json` is rebuilt from the log. `eccode audit` gains `warnings` for a task completed whose handoff was never recorded (a crash between the two commits); `eccode handoff record` fills the gap.

### Limits (F8)
- `limits.maxActiveRuns` (default 4): `run start` refuses `RUN_LIMIT` when that many runs are open. `limits.reserveUsdPerRun` (default off) holds budget back for runs in flight. Usage the engine was never given is recorded as unknown, never as `$0`: `run end --no-usage` records `null`, `recover` closes interrupted runs with the real elapsed time and unknown usage, tokens without a dollar figure and without pricing leave the cost unknown. Totals are a lower bound; `status`/`resume` say so and name the runs to fill in with `run correct`. `docs/usage.md` "Limits: what the engine enforces and what it only accounts" states which limits are enforced, which are self-reported and which only the host can enforce.

### Portability and release (F9)
- The review's five Windows failures were in the test suite, not the engine: fixtures needing `sh`, `grep`, `true`/`false` or `;` (absent on `cmd.exe`), POSIX-only quoting of `evidence run -- …` arguments, and test repositories whose checkouts rewrote LF as CRLF under a global `core.autocrlf=true`. `shellQuote` lives in `lib/util.js` (one copy) with a `win32` branch; fixtures are portable `node -e` programs and a static scan keeps them so; `tests/helpers.js initRepo()` creates every throwaway repository with `core.autocrlf=false`; `.gitattributes` keeps every text file LF on every platform and exempts the review-bundle logs and evidence logs. Windows itself was not run from this session: the fixes follow the analysis of the reviewer's log and are unverified until the CI job passes.
- `lib/index.js` is the package entry point; `npm run validate` checks `main`, every `files` entry, the plugin manifest versions and that `npm pack` ships the engine. Supported platforms declared (Linux and macOS with Node 18.17/20/22 gated by CI; Windows reported). An upgrade/rollback test installs the 0.1.0 toolkit, writes a record, installs the current toolkit over it, audits, and rolls back.

### Engine and CLI
- **Nine findings of a fresh-context red team closed, each with a regression test** (`tests/redteam-regressions.test.js`, RT1–RT9; the repro scripts were kept and re-run before fixing): symlinks inside task ownership reached the record (RT1); undeclared changes inside ownership were never pinned (RT2); plan ids `rework-N` collided with engine reworks (RT3); audit and status crashed with a TypeError on a tampered log instead of reporting `CORRUPT_LOG` (RT4); repeated `**/` globs were exponential and could hang the guard (RT5); implementer shell writes (redirects, `tee`, `cp`, `sed -i`) ignored ownership and `.git/` metadata was writable (RT6); a plausible `**/*.json` glob owned `.claude/settings.json` (RT7); secrets in `--label`, `--note`, handoff and review JSON reached the record and the handoff (RT8); a blocking finding pre-marked resolved without evidence passed (RT9).
- **`eccode rework extend <id> --files … --reason …`** (orchestrator or user) widens a pending rework after its review shows the defect reaches another file. Found while running Groundwork's rework-5: the independent reviewer rejected it because the same defect exists on the published-postmortem page, outside the rework's scope, and no engine path could widen it.
- **Post-delivery reworks work in the full delivery profile.** `rework open` on a record whose verification gate is approved told the user to reopen verification, but `gate reopen` accepted only escalated gates, so a defect found after delivery could not be fixed through the gates (found while fixing Groundwork's open defect). The user may now reopen an approved `verification` gate (`previousApprovals` keeps the earlier approval; the gate returns to `in_progress`), open a rework past `maxReworks`, and verification is redone before the next delivery. Approved phases and documents still cannot be reopened. Test: `tests/rework.test.js` "delivery profile".
- **Shipped records are replayed by the test suite.** `tests/records-replay.test.js` audits the TriageDesk, Groundwork, learning-cycle and toolkit records (hash chain, snapshot equals replay, approved artifacts unchanged) and checks the figures the reports cite (9 and 13 approved gates, 5 and 36 engine refusals, the operator's `gate.reopened` on `verification`). A reducer change can no longer drift from the published evidence.
- **Audit distinguishes pending re-review from unreviewed edits.** A file changed after approval whose current hash is already submitted to a later, not-yet-approved gate is reported as "Pending re-review" (a warning, exit 0) instead of a failure; delivery stays strict about both. This is the TriageDesk VER-2 situation, where the verification submission carried the final report versions and `eccode audit` said FAILED.
- **The final handoff lists every `--actor user` event** ("User decisions"), stating that they were entered on the user's behalf by whoever ran the CLI. The Groundwork delivery closed on operator interventions recorded as `--actor user`; the handoff now makes them visible instead of leaving them to the evidence README.
- **JSON inputs** (`--file`, `plan validate <file>`) resolve from the current directory, then the project root; a missing file is a `NOT_FOUND` refusal, not a stack trace.
- **`plan validate` warns** about ownership globs that point into `.eccode/` (other than `drafts/`): they never grant ownership, so a plan listing them is mistaken about what its tasks may write.
