# Pre-registered protocol: Phase 2 — does a debugging method and a behavior diff raise correctness on hard items?

Committed before any measured run; the git commit timestamp is the registration. Where this protocol says nothing, the multi-file run's protocol ([2026-10-27-mealie-multifile.md](2026-10-27-mealie-multifile.md)) applies, and through it the proof run's, the rerun's and the pilot's. The design is [docs/design/phase2-plan.md](../../docs/design/phase2-plan.md).

**Status: prepared, not launched.** Section 8 states the item count, arms, estimated cost and duration; the run starts only when the user approves that cost.

## Why

Phase 1 showed the engine makes work disciplined (tests in every run, proven regression tests, independent reviews, clean audits) and left open whether it makes work more correct (register row 59; the multi-file run's 12/18 against 9/18, p = 0.50). Gates catch failures after they happen. Phase 2 adds two capabilities meant to let the agent avoid them: the Debugging Lab (reproduce, hypothesize, test each hypothesis with executed evidence, confirm a root cause, prove on the pinned reproduction) and the behavior diff (every behaviour difference between baseline and candidate surfaced and classified; an undeclared one refuses delivery).

## Hypotheses and decision rules (register rows)

| Row | Hypothesis | Measure | Decision rule |
|---|---|---|---|
| H-A | On hard debug items, ECCode Phase 2 (the debug track with the Lab) resolves more items correctly than the bare agent | per item, the success rate of each arm (runs passing every hidden check / runs); the unit of analysis is the item, since runs on one item are not independent | **Primary:** paired permutation test (all 2^k sign flips of the per-item differences ECCode − bare; Monte Carlo above k = 20), two-sided, α = 0.05; met when p < 0.05 and the mean difference favours Phase 2. The same test is run for ECCode − ECC and reported. **Check:** a mixed-effects logistic regression with an item random intercept, likelihood-ratio test of the arm effect; reported beside the primary, not a second chance. **Secondary, labelled as such:** McNemar on runs (discordant pairs), which inflates significance by treating runs as independent |
| H-B | On a seeded set of unintended behaviour changes that pass the project's own tests, the behavior diff flags at least 90% | an unexplained difference reported for the seeded change, per item | met when flagged / seeded ≥ 0.90 (one-sided exact binomial against 0.90 reported beside it) |
| H-C | False refusals stay at or below 1 per run with the Phase 2 gates active | refusals labelled `false` by the refusal labeller (bench/pilot/refusals.js, labels by hand as in the multi-file run) per engine run | met when the mean is ≤ 1.0 |
| H-D | Cost and time per correct change, per arm | median tokens, USD (reported by `claude -p`) and seconds per run, divided by the correct runs | reported only; no pass/fail |

The fixture scorecard ([tests/fixtures/phase2/scorecard.md](../../tests/fixtures/phase2/scorecard.md)) is **not** evidence for H-B: it was used to build the diff. H-B is measured on seeded changes drawn after this protocol is committed (section 4).

## Items

**Minimum number of hard items (pre-registered, by simulation at item level; `bench/pilot/phase2-analysis.js power`, 400 simulations per point, seed 7).** Each simulated item draws a logit intercept u ~ N(logit 0.5, τ²); the bare arm passes a run with probability logistic(u) and the Phase 2 arm with logistic(u + log 2), so the average item moves from 0.50 to 0.67 as the multi-file run showed (engine 12 of 18, bare 9 of 18). **Stated between-item variance: τ = 1.0 on the logit scale** (item pass rates spread over about 0.12 to 0.88 at ±2τ; the multi-file run's three hard items spanned 0.17 to 1.0 per arm). Power of the primary test at α = 0.05:

| τ | runs per arm per item | minimum hard items for power 0.8 |
|---|---|---|
| 0.5 | 6 | 27 |
| **1.0 (stated)** | 6 | **32** |
| **1.0 (stated)** | **10** | **20** |
| 1.5 | 6 | 37 |

Simulated discordance at τ = 1.0 is 0.42, matching the stated 0.43; McNemar on runs reaches 0.8 at about the same item count, which is why it adds nothing as a decision rule and stays secondary. The earlier run-level number (115 pairs, 20 items at 6 runs, from Connor's formula) is superseded: it assumed independent runs.

**Design chosen: 10 runs per arm per item, minimum 20 hard items** (the same per-arm budget as 32 items at 6 runs, with fewer items to find).

**Go/no-go rule:**
1. Screening yields at least 20 hard items → **go**, at 10 runs per arm per item (up to 24 items, drawn with `mulberry32(42)` when there are more).
2. Fewer than 20 → expand the pool in this order, screening each addition the same way, until 20 are reached: Mealie `fix` commits from v3.10.0..v3.20.0; the realbugs selector's remaining BugsInPy projects; Mealie `feat` commits of at most 200 lines from the proof-run window.
3. Still fewer than 20 after the pool is exhausted → **stop**: report the screening, do not run arms 2 and 3, keep row 151 open. An underpowered run happens only as a protocol amendment the user signs before it starts, with the simulated power at the actual item count written next to it. No post hoc change of τ or of the effect assumption.

**Item selection rule (hard items from a separate screening run):**
- **Pool:** the realbugs suite's twenty bugs (bench/suites/realbugs) and Mealie `fix` commits from the proof and multi-file windows not yet used as debug items (bench/suites/mealie*), drawn as those protocols drew them.
- **Screening:** each pool item gets 3 bare runs (`--variant without --runs 3`). A **hard item** is one where at least one screening run failed a hidden check by the agent's own mistake (`agent-error` label, as in the multi-file run). Timeouts are `harness`, not hard.
- **Measurement:** every hard item, up to 24 (drawn with `mulberry32(42)` when there are more), is then run **fresh** in every arm: 10 runs per arm per item. Screening runs never count toward H-A (regression to the mean).
- **Items for H-B: the sealed seed set** (section 4a), produced by an agent that had not read the behavior diff's implementation, before this registration; each seed is run through `eccode behavior diff` once at measurement time (no agent involved; the engine is the subject).
