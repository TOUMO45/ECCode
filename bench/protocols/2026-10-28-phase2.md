# Pre-registered protocol: Phase 2 — does a debugging method and a behavior diff raise correctness on hard items?

Committed before any measured run; the git commit timestamp is the registration. Where this protocol says nothing, the multi-file run's protocol ([2026-10-27-mealie-multifile.md](2026-10-27-mealie-multifile.md)) applies, and through it the proof run's, the rerun's and the pilot's. The design is [docs/design/phase2-plan.md](../../docs/design/phase2-plan.md).

**Status: prepared, not launched.** Section 8 states the item count, arms, estimated cost and duration; the run starts only when the user approves that cost.

## Why

Phase 1 showed the engine makes work disciplined (tests in every run, proven regression tests, independent reviews, clean audits) and left open whether it makes work more correct (register row 59; the multi-file run's 12/18 against 9/18, p = 0.50). Gates catch failures after they happen. Phase 2 adds two capabilities meant to let the agent avoid them: the Debugging Lab (reproduce, hypothesize, test each hypothesis with executed evidence, confirm a root cause, prove on the pinned reproduction) and the behavior diff (every behaviour difference between baseline and candidate surfaced and classified; an undeclared one refuses delivery).

## Hypotheses and decision rules (register rows)

| Row | Hypothesis | Measure | Decision rule |
|---|---|---|---|
| H-A | On hard debug items, ECCode Phase 2 (the debug track with the Lab) resolves more items correctly than the bare agent | per item, the success rate of each arm (runs passing every hidden check / runs); the unit of analysis is the item, since runs on one item are not independent | **Primary:** paired permutation test (all 2^k sign flips of the per-item differences ECCode − bare; Monte Carlo above k = 20), two-sided, α = 0.05; met when p < 0.05 and the mean difference favours Phase 2. The same test is run for ECCode − ECC and reported. **Check:** a mixed-effects logistic regression with an item random intercept, likelihood-ratio test of the arm effect; reported beside the primary, not a second chance. **Secondary, labelled as such:** McNemar on runs (discordant pairs), which inflates significance by treating runs as independent |
| H-B | On a seeded set of unintended behaviour changes that pass the project's own tests, the behavior diff flags at least 90% | an unexplained difference reported for the seeded change, per item | met when flagged / seeded ≥ 0.90 (one-sided exact binomial against 0.90 reported beside it) |
| H-C | False refusals stay at or below 1 per run with the Phase 2 gates active | refusals labelled `false` by the refusal labeller (bench/pilot/refusals.js, labels by hand as in the multi-file run) per engine run | met when the mean is ≤ 1.0 |
| H-D | Cost and time per correct change, per arm | median tokens, USD (reported by `claude -p`) and seconds per run, divided by the correct runs | reported only; no pass/fail |

The fixture scorecard ([tests/fixtures/phase2/scorecard.md](../../tests/fixtures/phase2/scorecard.md)) is **not** evidence for H-B: it was used to build the diff. H-B is measured on seeded changes drawn after this protocol is committed (section 4).

## Arms

Same model (`sonnet`, as in every Mealie run), same items, same budget per run (`--timeout 7200`, `--max-cost` per process as the multi-file run), each run in a fresh sandbox:

1. **bare** — the bug report alone (`--variant without`).
2. **ECC** — [affaan-m/ECC](https://github.com/affaan-m/ECC) pinned at tag v2.2.3, commit `c05b2d6614f62f6db0047669aa4eefb223d478f9` (2026-10-01, "chore: retire the Everything Claude Code name, ECC only"), installed by `lib/bench.js` `installEcc` exactly as section 3a documents (`--variant ecc`).
3. **ECCode Phase 2** — the toolkit at this protocol's commit, installed in the sandbox, the fix asked through the debug track (`--variant debug`), whose engine now refuses a fix without the Lab's root cause and a proof on the pinned reproduction.

The ECCode Phase 1 arm is the same `debug` variant at commit `e3e8b75` (v0.15.0) and is run only if the budget allows a fourth arm; H-A compares arm 3 with arm 1.

### 3a. The ECC arm, exactly

Read from the pinned commit (`VERSION` 2.2.3; `.claude-plugin/plugin.json`; `hooks/hooks.json`; `scripts/lib/hook-flags.js`; `commands/orch-fix-defect.md`; `skills/orch-fix-defect/SKILL.md`; `README.md` on rules):

- **Install.** The whole repository (without `.git`, `node_modules`, `ecc2`, `docker`, `assets`) is copied to `<sandbox>/.claude/ecc/`; its `agents/` (68), `skills/` (293) and `commands/` (94) are copied to `<sandbox>/.claude/agents|skills|commands`, where Claude Code discovers them; the rule packs `rules/common` and `rules/python` are copied to `<sandbox>/.claude/rules/ecc/`, as ECC's README documents for a project install (rules cannot ship through a plugin). `.claude/ECC-PIN.txt` records the pin. Everything is committed before the agent starts, so it is the repository's starting point, not part of the change.
- **Hook profile: `standard`** (ECC's default; `ECC_HOOK_PROFILE` in `scripts/lib/hook-flags.js`, valid values minimal, standard, strict). Every group of ECC's `hooks/hooks.json` is written into `<sandbox>/.claude/settings.json` with each command prefixed by `CLAUDE_PLUGIN_ROOT="<sandbox>/.claude/ecc" ECC_HOOK_PROFILE=standard`, so the hooks resolve their own root and run with the standard profile. Events wired: PreToolUse, PostToolUse, PostToolUseFailure, PreCompact, SessionStart, Stop, SessionEnd. Hooks that need ECC's state store or session files write under `~/.claude` of the benchmark machine; the sandbox's `HOME` is the agent's as in every other arm.
- **Command flow.** The prompt (`lib/bench.js` `eccPrompt`) asks the agent to run `/orch-fix-defect <bug>`: the `orch-fix-defect` skill through the `orch-pipeline` engine, phase mask 0 → (2 if the root cause is unclear, with `code-explorer`) → 4 → 5 → 6; phase 4 writes a new failing regression test and fixes to green; phase 5 is `code-reviewer` (plus `security-reviewer` on a sensitive path); phase 6 is a conventional `fix:` commit behind GATE 2. The prompt tells the agent to treat GATE 2 as confirmed, since no human answers a headless run; GATE 1 applies only when a plan is produced. Skills the flow invokes: `orch-fix-defect`, `orch-pipeline`, and whatever the engine's phases pull in (`tdd-workflow`, `python-testing`, `verification-loop` are the documented candidates for a Python fix); which were actually invoked is read from the transcripts and reported.
- **What the arm does not have.** ECC's instinct learning and session memory start empty in every sandbox; its MCP configurations are not installed; its `ecc2` Rust alpha is not built. These hold for every run of the arm alike.
- **Checked.** `installEcc` was exercised once on an empty repository: the pin, the seven hook events, the 94 commands and the two rule packs are in place (not a measured run).

## Items

**Minimum number of hard items (pre-registered, by simulation at item level; `bench/pilot/phase2-analysis.js power`, 400 simulations per point, seed 7).** Each simulated item draws a logit intercept u ~ N(logit 0.5, τ²); the bare arm passes a run with probability logistic(u) and the Phase 2 arm with logistic(u + log 2), so the average item moves from 0.50 to 0.67 as the multi-file run showed (engine 12 of 18, bare 9 of 18). **Stated between-item variance: τ = 1.0 on the logit scale** (item pass rates spread over about 0.12 to 0.88 at ±2τ; the multi-file run's three hard items spanned 0.17 to 1.0 per arm). Power of the primary test at α = 0.05:

| τ | runs per arm per item | minimum hard items for power 0.8 |
|---|---|---|
| 0.5 | 6 | 27 |
| **1.0 (stated)** | 6 | **32** |
| **1.0 (stated)** | **10** | **20** |
| 1.5 | 6 | 37 |

Simulated discordance at τ = 1.0 is 0.42, matching the stated 0.43; McNemar on runs reaches 0.8 at about the same item count, which is why it adds nothing as a decision rule and stays secondary. The earlier run-level number (115 pairs, 20 items at 6 runs, from Connor's formula) is superseded: it assumed independent runs.

**Design chosen: 10 runs per arm per item, minimum 20 hard items** (the same per-arm budget as 32 items at 6 runs, with fewer items to find).

**Go/no-go rule:**
1. Screening yields at least 20 hard items → **go**, at 10 runs per arm per item (up to 24 items, drawn with `mulberry32(42)` when there are more).
2. Fewer than 20 → expand the pool in this order, screening each addition the same way, until 20 are reached: Mealie `fix` commits from v3.10.0..v3.20.0; the realbugs selector's remaining BugsInPy projects; Mealie `feat` commits of at most 200 lines from the proof-run window.
3. Still fewer than 20 after the pool is exhausted → **stop**: report the screening, do not run arms 2 and 3, keep row 151 open. An underpowered run happens only as a protocol amendment the user signs before it starts, with the simulated power at the actual item count written next to it. No post hoc change of τ or of the effect assumption.

**Item selection rule (hard items from a separate screening run):**
- **Pool:** the realbugs suite's twenty bugs (bench/suites/realbugs) and Mealie `fix` commits from the proof and multi-file windows not yet used as debug items (bench/suites/mealie*), drawn as those protocols drew them.
- **Screening:** each pool item gets 3 bare runs (`--variant without --runs 3`). A **hard item** is one where at least one screening run failed a hidden check by the agent's own mistake (`agent-error` label, as in the multi-file run). Timeouts are `harness`, not hard.
- **Measurement:** every hard item, up to 24 (drawn with `mulberry32(42)` when there are more), is then run **fresh** in every arm: 10 runs per arm per item. Screening runs never count toward H-A (regression to the mean).
- **Items for H-B: the sealed seed set** (section 4a), produced by an agent that had not read the behavior diff's implementation, before this registration; each seed is run through `eccode behavior diff` once at measurement time (no agent involved; the engine is the subject).

### 4a. The sealed seed set (H-B)

**Frozen implementation.** H-B is measured on the behavior diff as frozen in `bench/pilot/phase2-freeze.json`: commit `4f18441697b1ce4e7fe6d28d0893ecfdeb7ef92c`, `lib/behavior.js` sha256 `aabf35fa54c240c99ec003011c987a29f71430a582dd28fcdca0ed00b8c508c6`, `scripts/behavior/probe_runner.py` sha256 `03f949952541c0cd625e4ecbab62aeab25be5c38a16b5b06704ade3dfa35e2b4`. `bench/pilot/phase2-seeds.js` refuses to unseal or apply a seed when either file differs (`assertFrozen`); a change to either means a new freeze and a new registration before any measurement.

**Key incident and reseal (register row 154).** The first key reached the implementer's context through the seeding agent's report after the implementer's own read of the key file had been refused. The set is therefore re-sealed by the user under a key the implementer never sees (`bench/pilot/phase2-reseal.js`: old key from `ECCODE_SEED_KEY_OLD`, new key from `ECCODE_SEED_KEY`, prints neither, replaces nothing unless the round trip checks). The plaintext hash does not change; the new `sealedSha256` is registered below by the user after the reseal. **Validity after the reseal:** every seed is run alone against Mealie's full backend suite by `bench/pilot/phase2-seed-validate.js`, a worker that receives only the sealed file and the key from the environment and prints one `pass`/`fail` line per seed id; seeds that break a test are dropped (`--prune` re-seals without them) and the final counts and hashes replace the ones below.

- **Who:** a separate agent, briefed with the goal and the output format only, forbidden to read `lib/`, `scripts/` and `tests/` of this repository. It seeded changes into Mealie at the multi-file run's head commit `753325676331cf8df48cae7c64ce634f2cb693cb`, verified Mealie's backend tests stay green, and sealed the set.
- **Where:** `bench/suites/phase2-seeds/seeds.sealed` (AES-256-GCM; the key is held by the user, outside the repository) and `bench/suites/phase2-seeds/MANIFEST.json` (counts, kind labels, verification scope, hashes). The implementer of the behavior diff has not read the plaintext. `bench/pilot/phase2-seeds.js` unseals and applies a seed at measurement time, given the key in `ECCODE_SEED_KEY`.
- **Registered content:** see the manifest's `plaintextSha256` and `sealedSha256`, copied here at registration: `plaintextSha256 073cb5cfc25bf02cf6533a168701831610f7a05650bbdc643eab2780edaecca1`, `sealedSha256 46fe9a585a836345f7f3d888eba360af01e5456b20f4e041e66503f137036f1b` (21 unintended and 5 declared seeds on Mealie `753325676331`; baseline 3583 passed, 18 skipped, 0 failed; 8 seeds verified with the full backend suite, 18 with the test files of the touched modules; sealed 2026-10-28T20:51:56Z). The kind labels are in the manifest; the implementer has seen no description, file name or patch. `node bench/pilot/phase2-seeds.js verify` checks the sealed file against these hashes without the key..
- **Scoring:** a seed counts as flagged when its diff result has at least one unexplained difference (unintended seeds) or none (declared seeds, with their contract declared before the diff). Seeds whose verification scope is `partial` are reported in a separate line; the H-B rule is computed over all unintended seeds, and again over the fully verified ones.

## What runs, and where

- The machine, environments and `$AGENT_B` of the multi-file run.
- `eccode bench --variant without|ecc|debug --suite <suite> --tasks <hard items> --runs 6 --timeout 7200 --max-cost <per process> --save <runs.jsonl> --transcripts <scratch>`.

## Analysis

- H-A: `node bench/pilot/phase2-analysis.js analyze <runs.jsonl> --a debug --b without` (and `--b ecc`): the per-item table, the primary paired permutation test, the mixed-effects logit check (item random intercept, LRT) and the secondary McNemar on runs, in that order and so labelled. Implemented and tested before the run (tests/phase2-stats.test.js).
- H-B: count of seeded changes with ≥ 1 unexplained difference.
- H-C: false refusals per Phase 2 run, labelled.
- H-D: medians per arm and per correct run.
- Every stop, defect and amendment is appended to this file with its date before the report.
