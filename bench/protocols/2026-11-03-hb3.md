# Pre-registered protocol: H-B3, detector v3 on a new seed set

Committed before any v3 code and before any new seed; the git commit timestamp is the registration. Where this protocol says nothing, `2026-10-28-phase2.md` (sections 4a, amendments 1 to 4 and their event log) applies. The design is `docs/design/hb3-detector-v3.md`.

**Statement carried by every report of this work: H-B2 is a new seed set written after v2 was frozen; it is spent as a blind set (the implementer read its descriptions); the original sealed set remains unopened (key unavailable); the old 26 seeds are never cited as measured. H-B3 is another new seed set, written after the v3 freeze.**

## 1. Source

Owner decisions of 2026-11-03: (1) detector v3 approved, scoped: *in scope* (a) the example generator's support for `uuid4` and the other string formats found among the seven H-B2 misses of "inputs never produced", (b) `behavior.json` setup data and roles for the nine configuration misses; *out of scope, documented as limits:* request chaining, multipart, header capture, non-code files. (2) Design and pre-registration first; test-first with red and green evidence; all noise controls (comment-only edits, six layers) re-run on v3 before the freeze with zero unexplained differences; v3 frozen by hash and committed before any new seed exists; the primary threshold is 50 percent, 90 percent aspirational. (3) A new seed set by an independent agent under a new key (the owner keeps a second copy; never printed or logged), the same integrity analysis of its log, the same ten classes, at least four unintended per class, and intended seeds that must each show their declared change; acceptance counts only when the declared change is observed, and accepted-but-unobserved is reported apart. (4) Before any publication a second blind labeller on about ten misses, with agreement and kappa; the capability and configuration labels are reported as post-measurement judgments. (5) Round 1-lite: no paid run. (6) Agent compute (tokens) is recorded per task (`docs/build/compute-ledger.md`). (7) Standing rules unchanged; nothing is tuned after a result; evidence, not effort, is reported.

## 2. Hypotheses and decision rules

| Row | Hypothesis | Measure | Decision rule |
|---|---|---|---|
| H-B3a | **Primary.** On a new set of unintended, test-passing behaviour changes written by an independent agent, the frozen v3 behavior diff flags at least half | unintended seeds with at least one unexplained difference, over unintended seeds, after pruning | **Met** when flagged / unintended >= 0.50 (the point estimate). **Established** only when the exact Clopper-Pearson 95 percent lower bound is also >= 0.50. Both are reported; "met" without "established" is said to be that |
| H-B3b | **Aspirational.** At least 90 percent | the same | met when >= 0.90, as H-B in section 4a of the Phase 2 protocol; the one-sided exact binomial against 0.90 is reported beside it |
| H-B3c | v3 flags more than v2 on the same new set | paired per seed; exact two-sided sign test on the discordant pairs | reported, not a gate. v2 is run from its unchanged freeze worktree (`72d89a6`); v1 is not re-run |
| H-B3d | Intended seeds | four outcomes (section 5) | reported, no pass or fail; only "accepted and observed" counts as acceptance |

Per class, the 95 percent exact interval accompanies every rate. The intended-seed false-positive rate is reported separately and prominently, with the number of intended seeds whose declared change was observed as its denominator beside the total.

## 3. Prediction, stated before any v3 code

From the H-B2 post-mortem (register rows 180 and 181): of the 41 unintended H-B2 seeds, 9 were detected; 21 more depended on blockers that v3 addresses (8 on a required UUID4 input alone, 5 on input values the generator never produced, 8 on setup data or a role). If every one of those were converted, v3 would flag 30 of 41 (73 percent) on that set. Conversion will be partial, because an id must also hit an entity that exists, and because the dataset I build is informed by the H-B2 seeds and a *new* set will touch data I did not think of. I expect partial conversion of about half and a smaller gain from data that does not generalise.

- **H-B3a (50 percent):** I predict v3 flags **35 to 55 percent** of the new unintended seeds (point estimate 45 percent). The probability that it reaches 50 percent is, by my judgement, **below one half (about one in three)**. I expect the threshold more likely missed than met, and I register that expectation so that a miss is not a surprise and a hit is not oversold.
- **H-B3b (90 percent):** I predict it is **not** met (probability above 99 percent).
- **H-B3c:** I predict v2 flags about 15 to 30 percent of the new set (H-B2 gave 22 percent) and that v3 flags more than v2 on at least a third of the seeds more.
- **H-B3d:** I predict most accepted intended seeds will again be unobserved, fewer than in H-B2.
- **Blockers:** I predict the misses of v3 will be dominated by the limits that stay out of scope (chaining, headers, multipart, non-code files, the database engine, specific numeric inputs), and that the share classified capability stays above half.

If the data contradict a prediction they are reported as they are.

## 4. Order of events (fixed here)

1. This protocol and the design, committed (**now, before code**).
2. Tests written and shown red; code; tests shown green; the compute ledger kept.
3. The six comment-only noise controls of H-B2 and a six-baseline-run census, on v3: **zero unexplained differences in each control is a condition of the freeze**; if a control shows any, the cause is found and fixed before the freeze and the controls are repeated. `ignoreFields` grows only for fields the census shows to be random.
4. The **freeze of v3 by content hash, committed and pushed before any new seed exists** (`bench/pilot/hb3/` tools, a new freeze file; the freeze commit hash is recorded here before step 5).
5. A new 32-byte key, generated by a command that prints nothing, stored outside the repository with mode 600, never read, printed or logged by the implementer; a copy is handed to the owner as a file attachment, not as text.
6. The independent seeding agent, in a fresh context, given the committed brief for H-B3 and nothing about the detector, v2, v3 or H-B2's seeds, its results or its misses: the same ten classes, **at least 4 unintended per class**, 6 to 10 intended. Each **intended seed must show its declared change**: before sealing, the agent exercises the declared operation in the Mealie test client on the patched and on the unpatched code and confirms the responses differ in the declared way; a seed for which it cannot is not sealed. The sealing tool is the H-B2 one.
7. The integrity analysis of the agent's whole tool log by `bench/pilot/hb2/audit-agent-log.js` and the cross-check of every input and result for markers of the measured code, as for H-B2. **If it read any detector, probe, configuration or test file, H-B3 is marked "non-independent" in every table.** Every item the analyzer flags is listed and adjudicated, none exempted in the tool afterwards.
8. Validation by the registered rule (the whole backend suite per seed, in restart-tolerant chunks, as for H-B2) and the minimum: **at least 24 unintended seeds, at least 2 per class**, else stop and report before measuring.
9. Measurement: v3 (primary) from a worktree at the freeze commit, v2 (comparison) from its worktree at `72d89a6`, one engine run per seed, no agent, no paid model run, frozen-file hashes checked before and after by the driver and by independent recomputation.
10. **The results are hashed and committed before any seed description, file name, `observableBy` or patch is read.** Only then are misses classified (capability or configuration, by the H-B2 rule: configuration only if every blocker could be removed by what `behavior.json` can supply) and detections checked for attribution.
11. **A second blind labeller** labels about ten of the misses (a seeded sample, stratified when possible) from packets that contain the seed author's description, the named operation and the objective features, with the rule but without the first labels; agreement and Cohen's kappa are reported. Labels are reported as post-measurement judgments, not tested by a re-run. The same is done for a sample of the H-B2 misses before any publication of H-B2.
12. The report: per class and overall detections, misses and false positives with exact intervals; intended seeds in the four outcomes; every miss with its label and blocker; the compute ledger for the task; the caveats of the statement above; what the data support and what they do not.

## 5. Intended seeds: four outcomes

For an intended seed (its contract declared before the diff): **accepted and observed** (at least one difference, all explained by the contract, none unexplained); **accepted but unobserved** (no difference at all: the diff saw nothing; reported apart, not counted as acceptance); **false positive** (an unexplained difference on a declared change); **not verifiable** (a routing skip, insufficient coverage, an error). In H-B2 five of the seven accepted intended seeds were of the second kind.

## 6. What counts as tuning

After the freeze (step 4) nothing in the pipeline, the configuration, the brief or the seeds changes. A change is a new version, a new freeze and a new registration, and everything measured before it is reported as exploratory. No re-run with a changed configuration is made to test a label. The analysis code (`report.js` and its callers) is not frozen and computes no diff result.

## 7. Limits registered with this protocol (the register rows follow with the results)

Out of scope and expected to cause misses: request chaining, multipart and binary bodies, form-encoded bodies, response-header and file-name capture, non-code files as surfaces, a network fetch, the database engine, specific numeric inputs, the lenient coverage verdict. The seeds are written by an agent, not found in the wild; one codebase; the measurement is of the freeze commit and says nothing about later engine changes; the independence of the seeding agent rests on its brief and on the log analysis; v3 is informed by the H-B2 post-mortem, so a result on the H-B2 set would not be blind (none is claimed); agent compute is recorded in the ledger and is not metered by the benchmark meter, which stays at $0; Round 1-lite is not launched.

## 8. Amendment 1 (2026-11-03, before the freeze; no seed exists, no result exists)

Registered while building and testing v3, before the noise controls were accepted and before any freeze. It changes nothing in sections 2 and 3 (hypotheses, decision rules, prediction).

1. **Every seed must be shown, not only the intended ones (stricter than the owner's wording, and reported as such).** The owner asked that intended seeds each show their declared change. The H-B3 sealing tool (`bench/pilot/hb3/seal.js`, in the freeze) refuses a set unless **every** seed, intended or not, carries `verification.shown: true` and a `verification.evidence` (at least 40 characters) saying that the request was exercised on the unpatched and on the patched application and how the two responses differ. Reason: a seed that no request can show cannot be detected by any tool, and counting it as a miss would blame the detector for the seed. A seed the agent cannot show is not sealed. The sealing tool also refuses fewer than 4 unintended seeds in any of the 10 classes and any number of intended seeds outside 6 to 10, so the agent finds out before it seals. The brief is `2026-11-03-hb3-seeding-brief.md`. If the owner prefers the narrower rule, the cost is a set in which some seeds may be unobservable and the miss list must then separate them; the sealing tool would have to change and the freeze with it.
2. **The report counts four outcomes of an intended seed** (`bench/pilot/hb2/report.js`, not frozen): accepted and observed, accepted but unobserved, false positive, not verifiable; the false-positive rate is taken over the seeds whose declared change was observed, with the total beside it. The 50 percent threshold is *met* by the point estimate and *established* only if the exact lower bound reaches it; both are printed, with the 90 percent line. Tests: `tests/hb3-report.test.js`.
3. **The log analysis is the H-B2 one** (`bench/pilot/hb2/audit-agent-log.js`), made to recognise the H-B3 sealing command, key file and scratch directory, and to classify the rest of a chained command line instead of exempting the whole line when one segment is the sealing command (a hole found while generalising it; the H-B2 audit used the narrower exemption and its result is not changed by it).
4. **The Mealie setup (S1 to S4) is as built in `docs/design/hb3-detector-v3.md`, Amendment 1.**
