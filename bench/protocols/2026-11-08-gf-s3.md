# S3 protocol: one small FastAPI project, pre-registered (2026-11-08)

**Status: pre-registration, written before any S3 build.** It fixes the scope, the hidden acceptance suite, the metrics and the budget before the engine builds anything, so the result is measured against a prediction, not rationalised after. S3 is NOT started here. The owner approves this protocol before S3 begins. Base: branch `claude/wonderful-goldberg-o6u7m6`, head after S2.4.1. Standing rules apply; S2.3 stays suspended; S2.4 acceptance is the owner's event.

## B1 — Scope

**One small FastAPI project, built by the engine from an idea, in the reduced S3 of section 20 (backend and test groups only).**

- **Idea (fixed now):** a shared task tracker. Users register and log in; each task has an owner; a user sees and edits only their own tasks; an admin role sees all. SQLite storage.
- **Groups:** `backend` (owns `app/**` minus `app/db` and `app/auth`; here the whole app since there is no separate db/security group in the reduced S3, so backend owns `app/**`) and `test` (owns `tests/**`). Isolation per S2.4 (kernel sandbox, GF-ISO-0..4); the engine commits each group's work onto `gf/<group>` and merges in dependency order (GF-ISO-2/3).
- **Stack:** Python / FastAPI / SQLAlchemy / Alembic / SQLite — the only supported profile (L-GF-2).
- **Endpoints (5 to 7):**
  1. `POST /v1/register` — create a user (email, password), returns the user.
  2. `POST /v1/login` — returns a bearer token.
  3. `POST /v1/logout` — invalidates the token.
  4. `GET /v1/tasks` — the caller's own tasks (admin: all).
  5. `POST /v1/tasks` — create a task owned by the caller.
  6. `GET /v1/tasks/{id}` — a single task, **only if the caller owns it** (admin: any).
  7. `PATCH /v1/tasks/{id}` — edit a task, **only if the caller owns it** (admin: any).
- **The explicit authorization rule (makes BOLA/IDOR a tested requirement):** a non-owner, non-admin request to `GET`/`PATCH /v1/tasks/{id}` for another user's task returns 403 (or 404 without leaking existence), never 200 and never the other user's fields. This is the one real authorization rule; the hidden suite probes it directly as a cross-user access attempt.

**Template-first (G0.5 / GF-COST item 4).** The preferred start is a maintained skeleton. Candidates considered, with license and version-lag notes:
- **`fastapi/full-stack-fastapi-template`** (MIT): the official skeleton, but it is heavy (Docker, Postgres, frontend, CI) and more than one major behind in several pinned dependencies; adopting it would pull scope far beyond 5-7 endpoints.
- **`tiangolo/fastapi` project-generation docs** (MIT): guidance, not a runnable skeleton.
- **Decision for the reduced S3: no external template.** The project is 5-7 endpoints on one SQLite file; a maintained skeleton adds more surface (Docker, Postgres, auth libraries) than it saves and brings version-lag upgrades that are not worth it at this size. The engine builds from the sealed contracts. This decision itself is the G0.5 ADR (fork / borrow / buy / scratch → **scratch**, with the reason recorded). If the owner prefers a template, the full-stack template is the one to adapt, with a recorded upgrade task for every dependency more than one major behind (GF-COST item 4) before the build.

## B2 — Hidden acceptance suite

- **Written by a SEPARATE fresh-context agent from the PRD only**, before the build, with no sight of the engine's implementation. The agent receives the sealed PRD (the idea, the endpoints, the authorization rule) and writes pytest acceptance tests that drive the running app over HTTP (register, login, create, read-own, the cross-user BOLA probe, admin-sees-all, logout-invalidates).
- **Held by the engine and never visible to the build groups:** the suite is sealed by hash (GF-ACC-1/2, S3 scope) and write/read-denied to the backend and test groups (L-GF-7: read-denial depends on the harness running hooks on Read; on this host it is enforced, recorded as a limit otherwise).
- **Run at the end, once**, against the delivered app in a clean checkout, by the engine.
- **The builders' own tests are a second, separate measure:** the test group writes its own unit and integration tests during the build; these are reported separately from the hidden suite, never merged into it.

## B3 — Metrics (fixed now)

Recorded for S3 and reported at the end:
1. **Hidden-suite criteria passed of total** — the primary capability measure (e.g. 9 of 11).
2. **Cost per accepted criterion** — total processed tokens for S3 (usage snapshots at S3 start and end via `lib/greenfield/usage.js`) divided by the hidden-suite criteria passed; plus total processed tokens and a dollar estimate (Anthropic price page, dated).
3. **Wall time** — active build time.
4. **Gate refusals, split into friction vs capability:** a **false refusal** (the engine refused a correct action: a legitimate write the ownership rule wrongly blocked, a valid command the runner rejected) is friction and is counted separately from a **true refusal** (the engine correctly refused a cross-group or out-of-task action). Each refusal is logged with which rule fired and whether it was false.
5. **Escaped defects** — one independent review after delivery lists defects the hidden suite and the builders' tests both missed; reported as escaped.
6. **Illustrative comparator (n=1, labelled):** one bare Claude Code run on the same PRD and the same hidden suite, with no engine, as an illustration only. It is NOT the comparison — the real comparison is the G4 protocol (S6). Reported as "illustrative, n=1" with its hidden-suite pass count beside the engine's.

## B4 — Estimate and cap

- **S3 estimate (from the design doc, section 20's reduced S3 plus item 5):** the reduced S3 is **70 to 130 M** processed tokens (section 17 of `docs/build/gf-s2-evidence.md`), and section 20 gives **95 to 175 M** with item 5 (the contract-test generator and GF-API rules) folded in. For this one-project reduced S3 without item 5's full API ruleset, the registered estimate is **the reduced-S3 range, 70 to 130 M processed tokens**.
- **Cap = estimate + 25%** → **pause at 80% of the cap, hard stop at 100%**, checked after every step by a usage snapshot. With the top of the estimate 130 M: cap = **162.5 M**, pause at **130 M**, hard stop at **162.5 M**. With the midpoint 100 M: cap = 125 M. **The S3 session registers the exact cap from its chosen estimate point before the first build step**, and checks it after every numbered step, as this session's budget rule requires.
- **Metering requires a genuinely fresh session** (L-GF-73, and this session's experience): per-slice token deltas are only clean when the session starts empty. S3 MUST start in a new session so its start snapshot is near zero and the delta is S3's real cost, not a continuation's cache reads.

## Exit

S3 is built in a fresh session per the handoff (`docs/build/handoff-s3.md`), closed by the slice-closure rule (GF-CLOSE-1..6) or accepted with limits by the owner. The hidden suite runs last; the metrics above are reported against this pre-registration.
