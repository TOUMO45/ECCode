# Pre-registered protocol: real bugs — does ECCode find and fix them better, and what does the debug track cost?

Committed and pushed before any run of this batch starts; the git commit timestamp is the registration.

**Why.** Register row 59 is open: on the engine suite neither bare model made a mistake, so a correctness gain could not show. This batch uses real bugs from real projects (`bench/suites/realbugs`): twenty bugs reported and fixed in youtube-dl, black, tornado, thefuck and tqdm, at their pre-fix commits, with the fixes' own tests as hidden checks. It also measures the debug track (one owner, one reviewer, a regression test proven by `fix verify`, a mutation run, no verification gate) against the full quick track. And it separates the debugging method's text from the engine that enforces it.

**Design (fixed in advance).**
- Suite: `bench/suites/realbugs`, all twenty tasks. Selection and screening: `bench/suites/realbugs/_tools/selection.json` (seeded draw, three recorded exclusions); every task validated live (pre-fix tree fails the bug check and passes the regression check; the real fix passes both). No model has run these tasks except the pilot below.
- ECCode at this protocol's commit, run from a worktree pinned at it.
- Environment: `ECCODE_REALBUGS_VENVS` built by `_tools/setup.sh` (Python 3.8.20, pinned packages); repositories mirrored once into `ECCODE_BENCH_CACHE`; Claude Code CLI 2.1.310.
- Four variants, identical agent command, model alias `sonnet`, subagents inheriting the session's model:
  - `without`: the bug report alone;
  - `method`: the debug-investigation skill text prepended (reproduce first, isolate, root cause, prove the fix), nothing installed;
  - `debug`: the toolkit installed (`guard` profile), fix through the debug track (`.claude/commands/eccode/debug.md`);
  - `engine`: the toolkit installed (`guard` profile), delivery through the quick track (`.claude/commands/eccode/quick.md`), as in the earlier engine batches.
- Agent command: `cat PROMPT.md | claude -p --model sonnet --output-format json --allowedTools "Read Grep Glob Edit Write Agent Task Bash(python*) Bash(pytest*) Bash(node .claude/eccode/bin/eccode.js*) Bash(git diff*) Bash(git status*)"`
- n = 3 per task per variant: 60 runs per variant, 240 in all. Timeout 3,600 s per run.
- Seven `eccode bench --suite bench/suites/realbugs --runs 3 --timeout 3600 --save <file>` processes run at the same time, so that all four variants run in the same hours:
  - `without`, all tasks;
  - `method`, all tasks;
  - `debug` in two processes (the first ten tasks in suite order, then the last ten);
  - `engine` in three (tasks 1–7, 8–14, 15–20).
- **Primary outcome: a run passes when it passes both hidden checks** (`bug`: the tests only the real fix passes; `regression`: the other tests of those files, or of the project's offline suite, that pass before and after the fix).
- **Primary analyses, two:** `debug` vs `without` and `engine` vs `without`. Each is the difference in pass rate, tested by the permutation test stratified by task (labels shuffled within each task; 20,000 seeded resamples; two-sided), as `bench report` prints in its "all tasks" rows. The two p-values are Holm-corrected: the smaller must be below 0.025, then the larger below 0.05.
- Secondary outcomes:
  - the `method` vs `without` difference, the ablation: the text of the method without the engine;
  - `debug` vs `engine` in pass rate (same stratified test, reported with its p) and in cost;
  - which hidden check failed, per variant;
  - cost and tokens per run as the session reported them, with medians and ratios;
  - wall time;
  - for the engine variants: delivered with a clean audit, review rounds, and for `debug` whether fix verify proved the test and the mutation result;
  - for every undelivered `debug` or `engine` run, the cause read from its transcript.
- **Decision rules:**
  - Register row 59 ("the engine's effect on correctness is not measured") **closes** with a measured gain when either primary difference is above 0 and significant after the Holm correction. The row then states the variant, the size and this suite.
  - It **opens a defect row** when either primary difference is below 0 and significant after the correction.
  - Otherwise it **stays open**, restated with this result: no measured correctness difference on twenty real bugs at n = 3 per cell, which does not show the effect is zero. The cost ratios are then the headline result.
  - **The debug track counts as the lighter mode** when its median cost per run is at most 60% of the `engine` variant's and at least 80% of its runs deliver with a clean audit. Otherwise the register records what it missed.
  - Its cost against `without` is reported against the target set when it was proposed (about 2×; met at ≤ 2.5×).
  - **The method ablation** has no decision rule. Its difference from `without` and from `debug` is reported with p-values, and read as how much of any effect the text alone carries.
  - Any engine-variant run whose record fails its audit opens a register row as a defect.
- **Reporting:**
  - One report of all 240 runs, built with `bench report` from the seven processes' saved runs, is committed verbatim as `bench/realbugs-results/2026-10-24-realbugs-sonnet.md`, whatever it shows. The saved runs are committed next to it as `2026-10-24-realbugs-sonnet.runs.jsonl`. It carries the comparison tables, and `bench tally --dir bench/realbugs-results` recomputes the figures from it.
  - A run that fails for an infrastructure reason stays in the raw rows as it is and counts as a failure; nothing is re-run or dropped. Infrastructure failures are an API error, a timeout, or a session that ended with no result line. A sensitivity analysis without runs whose session never started (no result line, or zero turns) is reported next to the primary one.
- **Stopping rule:** one batch. These twenty tasks are not sampled again with `sonnet` in these four variants.

**Pilot, disclosed and excluded.** Before this protocol, one pilot ran thefuck-31 once per variant with `sonnet`, from commit 780116c, to validate the harness end to end:
- `without`: 2/2 hidden checks, 32 s, $0.13;
- `method`: 2/2, 32 s, $0.14;
- `debug`: 2/2, delivered with a clean audit, 96 s, $0.45. The transcript shows every step of the track in order, with no refusal: reproduction recorded failing, fix, `fix verify` PROVEN, mutation run, handoff, submission, one review, delivery by the orchestrator;
- `engine`: 2/2, delivered with a clean audit, 217 s, $0.87; no refusal in any agent's transcript.

Since the pilot, only the harness's reporting changed. `debug` runs now also record whether fix verify proved the test and the mutation result, and the report compares `debug` with `engine` as well as with `without`. The pilot is not part of the analysis.

**Amendment, before any analysis (2026-10-24).** The batch started at 02:51 UTC from 6fdf013 and was stopped at 02:54 UTC, when five runs had finished. Two of them were engine-variant runs that stopped before delivery, both for reasons that would have decided many runs independently of the variant compared:
- *tqdm-6 (`engine`):* the bug reports of the four tqdm tasks gave `python -m pytest -q tqdm/tests` as the test command. That command collects no tests: pytest collects only `test_*.py`, and tqdm's files are `tests_*.py`. The orchestrator pinned it, so the task could never complete. The fix itself passed both hidden checks.
- *tornado-15 (`debug`):* the fix was proven by `fix verify`, killed its mutant and passed both hidden checks. But the pinned module, `tornado/test/web_test.py`, holds a test that fails in this environment before any change, so the task could never complete.
- In both, the engine had no way to correct a pinned command on a one-task track short of the user abandoning the work item (register row 65).

Fixes, before the restart:
- **The bug reports.** The tqdm reports now name their test files. The builder now measures the tests that fail in this environment both before and after the fix, and every report names them, as a project's CI notes would. That applies to thefuck-22, thefuck-24 and thefuck-31 (two modules that fail to import and one failing test), tornado-13 and tornado-15. Nothing else in any report changed (bench/suites/realbugs/_tools/prompts.json, build.py).
- **The engine.** `task rescope --command` lets the orchestrator of a one-task track re-pin a released task's check. The change is recorded with its reason and the previous command. Both playbooks say when to use it, and never to hide a failure the change caused (lib/tasks.js, commands/quick.md, commands/debug.md, tests/debug.test.js).

**Second amendment, during the batch and before any analysis (2026-10-24, about 03:35 UTC).** tornado-13's regression check cannot pass in this batch, in any variant. The check includes `tornado/test/httpserver_test.py::UnixSocketTest::test_unix_socket`, which binds a Unix socket in the temporary directory. The batch processes run with `TMPDIR` set to a long per-process directory, chosen to keep each process's session transcripts apart. The socket path then exceeds the operating system's limit: `OSError: AF_UNIX path too long`. Reproduced at the fixed commit: the test passes with `TMPDIR=/tmp` and fails with the batch's 137-character directory. The live validation ran with the short default, which is why it passed there.

- The first runs of every variant on tornado-13 that reached the check failed it this way, with the bug check passing.
- The batch is not stopped. The artifact is the same for all four variants and every run, so tornado-13 becomes a stratum in which no variant can pass. Such a stratum adds nothing to the stratified tests' statistic or its permutation distribution.
- The registered analysis is reported unchanged, with tornado-13 scored as it falls.
- **A disclosed sensitivity analysis** scores tornado-13 on its bug check alone and repeats the primary and secondary tests. It is reported next to the registered one, never in place of it.
