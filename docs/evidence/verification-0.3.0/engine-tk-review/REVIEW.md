## Verdict: APPROVED

Both claims hold with evidence. The union of every `task.completed` event fixes the pinned set and the release-tree attribution exactly as described, the reducer and snapshots are untouched (no replay or audit difference on any shipped record), the review set can only grow (every path in the union came through `complete()`'s ownership, git-changed and undeclared-file checks, and ownership never narrows), and the CLI `audit` still reports every tamper I tried against a union-pinned record. The suite's leak of `~/.eccode/memory` is real on this machine (8 failures on the base commit, 0 on the branch, same home) and the isolation reaches every child process the tests spawn. Four **low** findings, none blocking; all are candidates for a follow-up.

## 2. TK-1: correctness

**The union.** `lib/tasks.js:504-513 filesChangedByTask(events)` walks the log once, starts a fresh map at `plan.imported` and adds `ev.data.filesChanged` of every `task.completed` to the task's set; `recordedFilesChanged(events, tasks)` (`:517-520`) unions the snapshot field on top for the given task ids only. I checked against the reducer (`lib/reducer.js:175-191` resets `s.tasks = {}` at `plan.imported`; `:202-210` overwrites `t.filesChanged` at `task.completed`): the union keys on the same `data.task`, resets at the same event, and the snapshot is always a subset of the log, so the extra union of `t.filesChanged` is redundant but harmless.

Cases asked for, with evidence:

- **Three completions** (`probe-lifecycle.js`): attempt 1 creates `a.js`, `b.js`; attempt 2 stages a rename `a.js → a2.js`, edits `b.js`, deletes `q.js` (present at the baseline commit); attempt 3 deletes `b.js`, adds `c.js`. Snapshot `filesChanged` = `[b, c]`; union = `[a, b, .eccode/drafts/api-notes.md, a2, q, c]`; **pinned = `[a2.js, c.js]`**, i.e. the surviving files only; after approval `unreviewedChanges` is `[]` and `eccode audit` exits 0. On the base library the same record pins only `[c.js]` and audits as failed before any tampering (`a2.js added after approval`, `q.js deleted after approval`).
- **`plan.imported` re-import**: the synthetic probe confirms the reset. Through the engine it cannot carry completions: `plan.imported` is committed on every plan *submission* (`lib/gates.js:191-196`), phase gates (and therefore claims) need the plan approved, and `reopenGate` (`lib/gates.js:596-603`) refuses an approved gate unless it is the verification gate. So the reset only ever mirrors the reducer on a plan that has no completed tasks.
- **A rework that deletes a first-attempt file** (`tests/phase-artifacts-after-rework.test.js` case 2, and attempt 3 above): the path stays in the union, `phaseChangedFiles` drops it with `exists()` (`lib/gates.js:90`), and `releaseTreeChanges` counts it in `reviewedDeletions` (`lib/delivery.js:144`), so after approval the deletion is not reported. Recreating it afterwards is reported `added after approval` (tamper 3).
- **`.eccode/drafts/`**: a handoff may declare a draft (`owns` allows `.eccode/drafts/**`, `lib/tasks.js:32`); it lands in the union and is filtered from the pinned set (`lib/gates.js:90`) and from the release tree (`excluded`, `lib/delivery.js:101`). Confirmed in the lifecycle probe (draft declared, not pinned).
- **Renames**: both paths are declared (NEW-4 rule), both enter the union, the old path fails `exists()` and is not pinned; recreating the old path after approval is reported (tamper 4).
- **Other phases' tasks**: `recordedFilesChanged` looks up only the ids passed in (`phaseTasks`), and ownership globs cannot overlap between tasks of the same plan, so no cross-phase leakage; the synthetic probe confirms the lookup is per id.

**Lock safety.** `Store.commit` (`lib/store.js:201-224`) runs the check callback inside `withLock` (`lib/util.js:75-108`, an `O_EXCL` lock file held by this process); `readEvents` (`lib/store.js:106-123`) takes no lock, so calling it from `phaseChangedFiles` inside the callback cannot deadlock, and because the writer holds the lock no other process can append while it reads. `repairTail()` has run before the callback, so the tail is whole. `taskFilesReader` in `lib/delivery.js:22-25` constructs a second `Store` on the same root for a read only; `unreviewedChanges` is called inside a review's commit (`lib/gates.js:529`) and from `eccode audit` on a replay (`bin/eccode.js:298`), both fine for the same reason.

**Performance.** One extra full read and parse of `events.jsonl` per phase submission, per review and per audit (two in `audit`, which also replays). The union itself is linear: 200 000 completion events in 115 ms. The largest shipped record has 789 events. No concern; noted as L4 for the record.

**Behaviour on existing records.** Unchanged: `probe-compare-records.txt` shows the same `unreviewedChanges` (`[]`) on all four records with both libraries, and no union delta on any task that was completed once. The reducer, store and schemas are not in the diff, so the snapshot digest of every event replays as before (the 257-test suite includes the replay tests).

## 3. TK-1: security and integrity

**Can the union pin a file the task never owned?** No. Every path in the union was written by `complete()` (`lib/tasks.js:410-431`): declared paths must be inside `t.files` (`outside` check), must appear in `git diff` since the claim (`missing` check), and in-ownership changes must be declared (`undeclared` check). Ownership only grows (`rework.extended` appends, `lib/reducer.js:313`); there is no narrowing event. The log is hash-chained, so a crafted `task.completed` would need the chain rewritten, which `audit` reports. The lifecycle probe's attempt 3 tried to restore `q.js` at its baseline bytes without declaring it: refused `INVALID_HANDOFF`.

**Can a file leave the review set?** The union only adds. The three places the new reader is consulted either widen the pinned set (`phaseChangedFiles`) or widen the set of changes *excused* from the unreviewed report (`reviewedDeletions`, in-flight attribution, `deletedInReviewedWork`). I looked for a path where the wider excuse hides an unreviewed change:

- *In-flight attribution* (`lib/delivery.js:153`): `filesOf(t)` is a subset of `t.files` (above), and the clause already skipped anything owned by an in-flight task, so the union adds nothing here. The in-flight probe edits a pending task's first-attempt file out of band and deletes a core-pinned file: the deletion is reported immediately with both libraries; the edit is pinned with its edited bytes at the next phase submission with the new library (the base library pinned only the rework file and reported the edit only at delivery as `added after approval`). Reviewed earlier, not hidden.
- *Reviewed deletions* (`:144`, `:154`) and *`deletedInReviewedWork`* (`:190-195`): a deletion is excused only if a completion of a task in an **approved** phase declared the path. The excused path either no longer exists at that submission (so it was not pinned there and the deletion was in a reviewed handoff), or it was recreated and pinned, in which case the pinned-file loop (`:197-212`) reports a later deletion. Tamper 5 (restore a reviewed deletion at its baseline bytes) and tamper 2 (delete a pinned file) are both reported.

**Does `audit` still detect edits to approved artifacts?** Yes, through the CLI: on the union-pinned record, `eccode audit --root <dir>` exits 0 clean and exits 2 with the right line for each of: edit `a2.js` (a file only the first two attempts touched) → `modified after approval`; delete `c.js` → `deleted after approval`; recreate `b.js` → `added after approval`; recreate `a.js` → `added after approval`; restore `q.js` → `added after approval` (`results/probe-lifecycle-8085001.txt`).

## 4. TK-2: isolation

- `tests/helpers.js:12-13` sets `process.env.ECCODE_SHARED_MEMORY` to a fresh `mkdtemp` directory at module load, before `require('../lib/project')`. The engine reads the variable at call time (`lib/memory/records.js:35-37 sharedDir`), so load order would not matter even if a test required `lib` first.
- **Child processes.** Every spawn in the tests passes `{ ...process.env, … }` (`grep -n "env:" tests/*.js`: guard, hooks, CLI, F6, security, memory, lessons-at-claim). `tests/review-F5-authority.test.js:33-38` builds its env from `process.env` and deletes only `ECCODE_TEST`, `ECCODE_NOW`, `ECCODE_ACTOR`. The engine's own spawns (`lib/evidence.js:59-66`, `lib/memory/search.js:79`) inherit `process.env`. Empirically: the branch suite ran under a home whose shared store holds the promoted lesson and passed 257/257, including the tests that spawn the CLI claim (`lessons-at-claim`) and the guard.
- **Tests that never load helpers**: `tests/records-replay.test.js` and `tests/templates.test.js`; neither claims a task nor touches memory (grep for `claim(|Memory|lessons|sharedDir`: no match). No test reads `os.homedir()`; `lib/install.js:38` does for `--scope user` but no test exercises that scope.
- **`memory.test.js`**: sets `process.env.ECCODE_SHARED_MEMORY` to its own directory in its own fixture (`:17`) and passes it to its CLI children (`:135`, `:161`, `:205`); it has no test of the home-directory default, so nothing needs the helper's value restored. The only test that deletes the variable is the isolation test, which restores `HOME`, `USERPROFILE` and the variable in `finally`.
