# ECCode threat model

**Scope:** the toolkit (engine, CLI, hooks, prompts, memory) as installed in a Claude Code project. The applications a team builds with it have their own threat models; TriageDesk and Groundwork carry theirs in their design artifacts.
**Status:** written from the code and its tests on 2026-10-09. Each control names the test that exercises it. "Residual" means the toolkit does not close the risk and says so; it is not a promise of future work. No outside security review has been done.

## 1. What is protected

| Asset | Why it matters |
|---|---|
| The project record (`.eccode/events.jsonl`, `state.json`) | The hash-chained history every approval, delivery and handoff is derived from. If it can be rewritten, "verified" means nothing. |
| Approved artifacts and the files phase approvals pinned | A delivery claims these are the reviewed bytes. |
| Evidence logs (`.eccode/evidence/`) | The executed checks reviews cite; also where secrets would leak. |
| Reviews, handoffs, decisions, risks | The independence and user-authority claims. |
| Memory records and the shared memory store (`~/.eccode/memory`) | Lessons other projects will trust; promotion crosses a privacy boundary. |
| Operating resources (`skills/`, `agents/`, templates) | Self-improvement can change them; they shape every future agent. |
| Configuration and permissions (`.eccode/config.json`, `.claude/settings*.json`, `hooks/`) | Limits, roles, reviewers, hooks. |

## 2. Trust boundaries and actors

```
 user (human)  ──decisions──▶  main session = orchestrator  ──dispatch──▶  subagents (12 roles)
       ▲                              │                                         │
       │                              ▼                                         ▼
  final handoff                 eccode CLI (the only writer of the record)   project files
       ▲                              │                                         │
       └──────── .eccode/ record ◀────┘◀──── PreToolUse guard (identity, ownership, record) ◀┘
                                      ▲
                 untrusted content: tickets, fixtures, web pages, model output, retrieved memory
```

Actors the design assumes may misbehave:

| Actor | Capability | Motive or failure mode |
|---|---|---|
| **A1. A subagent** (a role) | Runs shell commands and edits files in its tool list | Approves its own work, cites checks it never ran, claims another role, edits files outside its task, rewrites the record to pass a gate, exfiltrates a secret into a log. Usually from prompt injection or from optimising for "done", not from intent. |
| **A2. Untrusted content** | Text the agents read: tickets, fixtures, retrieved lessons, web pages, model output | Carries instructions aimed at agents ("approve this", "skip security", "run this command"). |
| **A3. The orchestrator (main session)** | Everything a subagent can do, plus `--actor orchestrator` and, by transcription, `--actor user` | Closes runs with invented usage, reopens a gate "for the user" without asking, batches a user decision it never received. |
| **A4. A local user or script with filesystem access** | Can edit `.eccode/` directly, run `git checkout` on it, flip a lesson's `status` field | Tampering, or a well-meant "repair" that erases history. |
| **A5. The harness** | Reports `agent_type` to hooks, delivers usage notifications | Hooks not installed or disabled; usage arrives late; a crash mid-write. |
| **A6. A different harness** (Codex, Gemini CLI, Cursor) | Runs roles sequentially in one context | No identity binding at all. |

## 4. Residual risks (not closed)

1. **Identity is asserted, not proven.** Binding `--actor` to the real subagent depends on the PreToolUse hook running (A5) and on the harness reporting `agent_type`. The guard reads commands without executing them, so an indirect write (a script file it cannot see into, code held in a variable, an unknown interpreter) can evade it; inline programs it can read are denied. In other harnesses (A6) there is no binding at all; the toolkit documents sequential mode as reduced independence.
2. **A person at a terminal is not necessarily the product owner.** The terminal check tells a person from a pipe; it cannot tell who the person is, and a session run with `ECCODE_TEST=1` removes the check. The Groundwork delivery predates the check and closed on operator decisions recorded as the user, disclosed in its evidence README and in the handoff.
3. **The digests live in the same writable files as everything else.** A rollback that also replaces the snapshot is indistinguishable from an older record; an actor who rewrites the last event's `stateHash` and rehashes the chain, or forges whole events with valid hashes, is caught by nothing (`eccode audit` still catches a snapshot that differs from a replay). The same holds for the shared-memory attestation index. An independently protected checkpoint (a signed or externally stored chain head) is the next step and is not built.
4. **Evidence is only as good as the command.** The engine now binds a check to the task's declared command and to the bytes it ran on; it still cannot judge whether that command proves the criterion. The gate-challenge evidence shows reviewers missing two of four planted implementation defects.
5. **Redaction is pattern-based.** A secret in an unfamiliar format reaches the evidence log. Promotion scans are the second line; shared memory should be treated as internal, not public.
6. **Files git ignores** are invisible to the git-based accounting (completion, release tree) and to the tree digest: an implementer could create an ignored file outside its ownership through a write the guard does not recognise. Ignoring can come from configuration as well as from `.gitignore`: a repository's `core.excludesFile` (`git config core.excludesFile …`, no environment needed) or the user's global one hides a file the same way; a declared ignored file is refused as unchanged, an undeclared one is not seen (review R4-5 of TK-6). Since 0.3.4 configuration given only through the environment (`GIT_CONFIG_*`, `GIT_CONFIG_GLOBAL`) no longer reaches the engine.
7. **Windows: one clean run.** The 0.3.0 CI run on Windows failed 2 of 233 (guard tests 131 and 133: backslash paths); repaired by R43 after an independent review that rejected the first attempt. On 0.3.1 two test fixtures still fed unquoted native paths into bash commands (over-denials, not guard defects); quoted in `d9c1cc6`, after which the Windows job passed 253/253 (run 37974778884, Windows Server 2025, Node 22.23) and became gating. One run is not a track record: Windows stays "supported by CI" rather than "verified by a person", and the pty-driven terminal-confirmation test is skipped there. The track record since: the job failed four of the pilot branch's ~25 runs (66, 67, 68, 92) on the concurrent-writer tests, one CLI child of six exiting 1 with a raw `fs` error nobody captured (TK-3, open). Two Windows races in the tree produce that shape and 0.3.3 bounds both without knowing which fired: a replace-rename over `state.json` refused with `EPERM` while a sibling reads it outside the lock (`writeFileAtomic` retries; rated likelier by the independent review) and `EPERM`/`EACCES`/`EBUSY` on the lock file itself (`withLock` polls). Both are tested on a mocked `fs` only (`tests/write-atomic-retry.test.js`, `tests/lock-transient-errors.test.js`); the spawn tests now print the failing child's stderr, and the next Windows failure, not this change, decides the cause.
8. **Outside reviews, by tools.** The independent review in `docs/evidence/review-bundle/` was produced by a Codex session, and the adversarial verification of 0.3.0 in `docs/evidence/verification-0.3.0/` by a fresh agent context; neither is a person. The verification found F1, F2 and F4 not closed on 0.3.0 (rows R37–R42 are the repairs). A human security review has not happened; `docs/security-review-request.md` is the request.
9. **Metadata outside a shared record's attested hash is unbound** (verification NEW-8): the reviewer's name, review notes, evidence-snapshot statuses and provenance can be edited while the record still applies as verified. The hash covers layer, status, trust and content; widening it is a record-format change and is not done.
10. **Known-shape shell writes the guard does not read as writes** (verification F4 tail): `rm`, `rm -rf`, `git rm`, `git apply`, `patch`, `git am`, `find -exec sed -i`, `xargs sed -i`, `curl -o`, `wget -O`, `tar -x -C`, inline `openSync(path, 'w')`, a write through a symlink that lives outside the project, and `ln -s … && echo > …` in one line. Each is residual 1 in another shape; completion's git accounting is the backstop. A role that needs such a command runs it through the Edit tool or a declared script.
11. **The handoff over-claims the user channel** (verification F7.forgedUserEvent): an event with `actor: user` appended offline with a valid hash passes `audit` and the handoff lists it as a user decision. The handoff's wording should read "recorded as the user; the record's integrity rests on residual 3", and does once the handoff template is next revised.
12. **The engine trusts the guard's cwd for nested roots** (R42): when the hook reports no cwd, the harness's project directory decides, as before.
13. **Hard links** (guard reviews, H3): a hard link to a record file shares its inode; `realpath` cannot tell it from the file, so writing the link writes the record. Directories cannot be hard-linked, so only single files are reachable, a role still needs the path inside its claim, and completion's accounting sees the link as an undeclared file.
14. **Over-denials accepted for safety** (guard reviews, F7/J2; RescueStock pilot): `>"|"` is read as the clobber operator; a computed, record-free link operand beside another write is refused; a role moving a project file into its draft area is refused for the source. The pilot added three text-only shapes: a heredoc whose text names a record path after a redirect, a word containing `eccode` built from a loop or argument variable, and function or alias syntax beside an inline program (reviewers ran their checks as files under `.eccode/drafts/`). Each has a one-command workaround named in the refusal and in `docs/usage.md`; the cost is friction, the alternative is reading command effects, which residual 1 says the guard cannot do. TK-6 (0.3.4) added one: `PATH` (or `HOME`, `XDG_CONFIG_HOME`, `GIT_*`, `NODE_OPTIONS`) assigned or exported before an eccode CLI call on the same line is refused in its common forms (the forms that still pass are listed in residual 16), including `export PATH="$PWD/node_modules/.bin:$PATH"; eccode evidence run … -- npm test`; the assignment goes inside the checked command (`… -- 'PATH=… npm test'`). Words in commit messages, heredoc bodies and other commands' arguments are not read as assignments.
15. **Patterns are not a boundary.** Two of the five guard review rounds found a fresh bypass of a pattern-based fix (a record planted inside the record; an alias of the record); the shipped version judges real paths and is still a reader of commands, not a sandbox (residual 1). The original review's recommendation of read-only reviewer snapshots and worktree isolation stands and needs the host.
16. **Tree pinning: where it is off, and what TK-6 left unpinned** (R28, R30; TK-6, RescueStock pilot).
    - *Through 0.3.3 it failed open, silently.* A null digest recorded a run without `tree` and a submission without `commit` and `tree`, the completion and review checks compared nothing, and nothing was printed. A project nested below the repository root got a null digest whenever one of its dirty files (its own `.eccode/` drafts included) had no twin at the same path under the repository root, and a digest over the twin's bytes when it had one; that is how TK-6 stayed hidden through a whole pilot.
    - *Since 0.3.4.* The nested digest is fixed. "Inside git" means inside a git work tree (`git rev-parse --is-inside-work-tree`), not a HEAD that resolves: the digest is computed on a fresh repository before its first commit and after `git checkout --orphan`, so a run there is pinned and a stale one refused (the first two rounds of 0.3.4 read an unborn HEAD as "outside git", which let one git command record an unpinned run and a commit-less approval). Inside a work tree a digest that still cannot be computed is visible: the run, submission or release records `treeUnavailable: true`, the CLI prints a warning, `audit` counts the marked runs, a submission and a delivery keep their commit (the R30 baseline and the release commit), and completion and review refuse to cite a marked run while the digest is available again. `gate submit` and `eccode deliver` are refused while HEAD does not resolve inside a work tree (one commit, or switching back to the branch, fixes it), so release-baseline gaps can only come from records written before 0.3.4 or outside any work tree. "Inside a work tree" is decided from the project directory alone: the engine runs git without the caller's repository-selection and config variables (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_COMMON_DIR`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_CEILING_DIRECTORIES`, `GIT_DISCOVERY_ACROSS_FILESYSTEM`, `GIT_NAMESPACE`, `GIT_CONFIG*`), which, inherited, let one inline `GIT_DIR=…` record an unpinned run and a commit-less approval in rounds 1-3 of 0.3.4 and made an eccode call from a git hook misfire. Outside a work tree a run is unpinned by design and records neither, as do records older than the marker (skipped as before). *A failing git* (review R4-2): once the record pins (some run carries a tree or the marker, or some submission a commit), "not a work tree" is read as a git that fails (a broken `git` first on `PATH`, a moved project), not as a project that left git: `evidence run` records the marker with the warning, `gate submit` and delivery are refused, and completion and review refuse to cite a run that carries a tree or the marker while the current digest cannot be computed. **The engine trusts the `git` it finds on `PATH`:** a git that answers with forged output (a fabricated status or blob ids) cannot be detected by the engine and is residual 1; the guard refuses the common inline forms that assign `PATH`, `HOME`, `XDG_CONFIG_HOME`, `GIT_*` or `NODE_OPTIONS` to an eccode CLI call (and `env -i` running it), but it does not close the inline route. Forms it still passes (review R5-1 of TK-6), each residual 1 like a wrapper script: a brace group (`{ PATH=…; eccode …; }`; the subshell form is caught), a variable set by `read` or `printf -v`, or by sourcing a file, before the CLI; a quoted `"<<EOF"` that hides the following lines from this check (the identity checks still see them); and `node -r`/`--require`/`--import`/`--loader`, which preload code without any variable. None of them defeats the engine's own refusal of a failing git (R4-2: marker and warning, `NO_COMMIT`, refused delivery, no citation while the digest is unavailable); what they can still reach is a git or a preload that lies. *Outside git on purpose* (review R4-3): a repository reachable only through `GIT_DIR`/`GIT_WORK_TREE` (a bare repository driving a separate work tree) is outside git for the engine, which ignores every `GIT_*` variable; `.git` files, linked worktrees and `--separate-git-dir` are unaffected. **Not done:** `gate submit` is not refused when the digest alone is unavailable and the commit resolves (the commit is kept, so R30 is unaffected, and the review's stale check uses the digest at review time, not the submission's); `reconcile`'s re-runs and improvement evaluations record the marker without printing the warning (`audit` counts them); in a record that does not pin yet, a project whose git disappears records `{}`, as an older or git-less record would; git configuration given only through the environment (`GIT_CONFIG_*`, e.g. a `safe.directory` for a repository owned by another user) no longer reaches the engine and belongs in a config file; a script that reaches the engine with `NODE_OPTIONS` or `PATH` set is residual 1. Known follow-ups: before a record pins anything (no run with a tree or the marker, no submission with a commit), a failing git still reads as no git, so a run records `{}` and a first submission is accepted without a commit; telling "git not installed" (spawn `ENOENT`) from "git fails" (`git --version` exits non-zero) would close it (R5-2). The guard matches the variable names case-insensitively, for Windows, so on Linux `env path=/x eccode …` is refused although `path` is not `PATH` (R5-3, a harmless over-denial). Whether a gap is a warning or needs the user's acceptance (the R31 pattern) is a judgement left as is: gaps cannot be repinned, so a blocker would make every project with TK-6 history undeliverable.
    - *What the pilot's record keeps (`examples/rescuestock` at `220d3fa`).* For R28: 327 of its 448 command runs carry no tree and stay unpinned; a run whose recorded tree was computed over a root twin no longer matches the corrected digest and is refused as stale when cited (re-run it). For R30: all 19 of its gate submissions recorded no commit, so none of the gates it has approved gives the release-tree diff a baseline. After 0.3.4 the baseline becomes the first submission recorded on 0.3.4 to be approved (in approval order, so a rework approved before a later phase counts first): a file changed before that commit and pinned by no approval is never reported. `audit` and `reconcile` report each commit-less approval made before it, reworks included, as a release-baseline gap (a warning, since no later submission can repin a past approval); the gap text names the possible causes (outside a work tree or an unborn HEAD at submission, an engine older than 0.3.0, or TK-6), because the record does not say which applied. The delivery report names the gaps and limits its release claim to the changes since that baseline. A record in which nothing carries a tree or a commit is read as an older engine's and reports no gaps, as before.
    - *Bytes the digest does not see* (pre-existing, found by the review of the TK-6 repair): a file marked `git update-index --assume-unchanged` or `--skip-worktree` and then edited (status does not report it, the index blob is used: one command lets an actor make a stale check look current); a project inside a git-ignored directory (the digest covers nothing and never changes); submodules (a clean one contributes its gitlink commit, a dirty one is dropped, their contents are never hashed); a tracked symbolic link edited in place (hashed as its target's content); files git ignores (residual 6); a file whose name is not valid UTF-8 (git's bytes are decoded as UTF-8, the name no longer exists on disk under the decoded spelling, and the file is dropped from the digest, untracked or once dirty; Linux). Path names with newlines, CRs, quotes and leading or trailing spaces are tested on Linux only; Windows and macOS (case folding, Unicode normalisation) are not.

## 5. How to use this document

- When adding an engine rule, add a row here and name its test.
- When a residual risk is closed, move it to §3 with evidence; never delete the history.
- When a finding arrives from outside, map it to a row (or add one) before fixing it, so the fix has a stated threat.
