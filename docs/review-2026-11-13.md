# ECCode review against its goal, and the fix plan (2026-11-13)

**Goal (owner):** a plugin and tool that lets any coding agent, including a weak or small model, build medium and
large projects at high quality with little human interaction.

**Verdict:** ECCode's engine is sound in its foundations but does not yet serve that goal, for five reasons that
this review found, measured or reproduced. None is "the idea is wrong". Four of the five are about the process
being too heavy and too hard to follow; one is a hole in the promise the gates make.

**Method:** three independent read-only reviews (process cost measured by driving the CLI end to end; engine
defects by experiment; model-facing instructions), then the lead reproduced the most serious claims. Marks:
**[R]** reproduced by the lead, **[V]** verified by a reviewer with a command or file:line, **[I]** inferred.

## 1. What the evidence says

- Pilot W1 (`docs/build/weak-model-pilot.md`): Haiku with ECCode equalled Haiku alone on quality and hit the
  40-minute limit in 6 of 6 runs; Haiku alone took about 2 minutes.
- ECCode's last full build (`docs/build/gf-s3-evidence.md`): 86.4M tokens, of which the two builders used 12.9M
  (15%). 97% of all tokens were cache re-reads; the orchestrator's context grew to about 400K per message. **[R]**

## 2. The five root causes

### A. Every idea gets the heaviest process
- `/eccode:start` never chose a track; the documented `init` defaults to `greenfield`. **[R]** (`lib/reducer.js` TRACKS)
- Minimum for a toy project on that path: **30 commands, 12 hand-written files, 5 gates, 7 roles, 13-15 agent
  dispatches**; on the quick path: 12 commands, 4 files, 2 gates, 5 dispatches. **[V]**
- No size or risk classifier exists anywhere in `lib/`. **[V]**
- The quick path refused a plain Python project and an empty repository ("No test command detected"), which is
  exactly what the pilot's projects were. **[R]**

### B. The lead agent carries the process in its head
- The orchestrator must hold about 2,000 words of rules and wrap every dispatch in `run start`, `run end` and
  `status`: 45+ orchestrator calls before any code is reviewed. **[V]**
- A full standard delivery puts 14,500-16,000 words in front of models. About 7,000 of the 22,500 words of
  instructions are duplicates (one 148-word block appears 15 times). **[V]**
- Eight commands the engine demands on the standard path (`design alternatives/decide/adr`, `guard route/api/
  release/ack`, the ADR citation) appear in no instruction file. They are discovered one refusal at a time. **[V]**

### C. Exact files from memory, and errors that do not say the next step
- Review JSON is hand-written five times against a strict schema; plan JSON has 12 task fields; neither has a
  draft command (handoffs do, and no agent file mentions it). The schema paths named in the text do not exist in
  the user's project. **[V]**
- After a rejected review, `status` tells the agent to resubmit unchanged, which leads to escalation in three
  rounds. **[V]** Ten refusals name no next command or a command that cannot work. **[V]**

### D. The gates could be passed without the work being right
- **A project whose tests fail could be delivered.** The reviewer's "own passing check" could be any command,
  such as `true`. Reproduced: both gates approved, `Delivered`, real `npm test` exit 1. **[R] Fixed, section 3.**
- Evidence is not tied to the task, the actor or the state of the files: a passing run recorded for another task
  before the code was broken still completed the task. **[V]**
- `evidence run` exited 0 when the check failed. **[R] Fixed.**
- A re-chained forged log passes `audit` unless an anchor commit is given. Documented limit. **[V]**

### E. It stops for a human, and only works fully under Claude Code
- Three rejections or three task failures lock the record; every exit needs `--actor user`, also in headless
  mode. **[V]**
- 27 places tell the agent to ask, show or stop; 17 of them could be decided and recorded by the agent.
  Decide-and-record applies only when `ECCODE_HEADLESS=1`; the default is to ask. **[V]**
- Role separation and user authority are enforced only by Claude Code's Bash hook. Without it one process can act
  as author and reviewer, and `--actor user` just works. The hook does not cover PowerShell. **[V]**
- `export agents-md` produces 11,274 words with no procedure a single non-Claude agent could follow. **[V]**
- Budget and time limits are checked at four points from self-reported figures and can be cleared by the agent;
  there is no wall-clock stop. **[V]**

Also found: a torn last line in the event log silently loses a write and then bricks the record; a lock held
longer than 30 seconds by a live process is stolen; read-only shells give stack traces. **[V]**

## 3. Fixed in this change (all tests pass: 1,858 tests, 1,798 pass, 0 fail, 60 skipped)

| Fix | Where | Test |
|---|---|---|
| A reviewer must run each **pinned** verification command itself after the submission; the refusal prints the exact command | `lib/gates.js` | `tests/review-pinned-check.test.js` (1, 2) |
| `evidence run` exits 3 when the check fails (a reproduction may still fail and exit 0) | `bin/eccode.js` | same file (3) |
| Quick path starts on a plain Python project with unittest files; when nothing is detected the error is the whole next command | `lib/quick.js` | same file (4) |
| `/eccode:start` routes small work to the quick path by a stated size rule; `orchestrate` states the rule and the measured cost of the full path | `commands/start.md`, `skills/orchestrate/SKILL.md` | text; effect not yet measured |

One existing test (`tests/lab.test.js`) used a trivial reviewer check and was changed to run the pinned command.

## 4. Fix plan, in order of effect on the goal

Each item has a check that says when it is done. Do them in this order; re-run pilot W1 after P1 and after P2.

### P1. Make small and medium work cheap (root causes A and B)
1. **The tool chooses the track.** `eccode start "<idea>"` picks quick, feature or greenfield from what it can see
   (empty repository, files and lines the idea names, stack) and prints the path. *Done when:* the toy project
   needs at most 8 commands and 3 dispatches from start to `Delivered`.
2. **Quick has no separate verification gate** (as `debug` already has none); its last-gate checks move to the
   phase gate. *Done when:* quick is at most 2 hand-written files and 1 review.
3. **Draft everything.** `gate review --draft`, `plan draft`, a generated verification report; every agent file
   names `handoff draft`. *Done when:* no step requires JSON written from memory.
4. **Run accounting is automatic**: `gate start` and `task claim` open the run, `gate review` and `task complete`
   close it. *Done when:* `run start/end` appears in no instruction file.
5. **Cut the orchestrator to a loop**: "run `eccode status --brief`, do NEXT", about 400 words; move fix, refactor
   and debug text to track-only files; remove the duplicated blocks. *Done when:* a standard delivery reads under
   5,000 words in total.

### P2. Never leave the agent without a next step (root cause C)
6. Every refusal and every `status` prints one exact next command; list pending track rules before the refusal
   (the eight hidden commands). *Done when:* a script that only executes NEXT lines delivers the toy project on
   every track.
7. After `changes_requested`, NEXT is the task reset, and an unchanged resubmission is refused.
8. No stack traces: read-only shells, empty handoff JSON, closed pipes all give a coded message.

### P3. Make the promise true (root cause D)
9. Bind evidence to its task, its actor and a fingerprint of the task's files; `deliver` re-runs the pinned
   commands. *Done when:* the two reproductions in section 2D are refused.
10. Torn log tail is truncated before append; a lock is broken only when its holder is dead; add `eccode repair`.
11. `deliver` warns when no anchor commit protects the log.

### P4. Unattended, and any agent (root cause E)
12. Decide-and-record is the default; a human is needed only for spending, irreversible actions, access and a
    change of goal. Escalated gates and tasks have a recorded headless exit. *Done when:* no state needs
    `--actor user` to continue, outside those four causes.
13. A real budget: per work item, wall-clock included, checked on every command, not clearable by the agent.
14. Role separation that does not depend on one host: a per-role token set by the dispatcher, or an honest
    single-agent mode that says separation is by convention. The hook covers PowerShell.
15. `export agents-md` becomes a single-agent procedure: one rules block, no host tool names, templates inline.

### P5. Prove it (the claim itself)
16. Re-run W1 after P1 with a longer limit and cost reported for runs that time out.
17. Find a medium project that the weak model alone fails (three plain runs first), then compare with ECCode.
18. Only then decide Stage 2 or the direction rule in `docs/build/gf-s4-decision-rule.md`.

## 5. What is sound and should be kept
- `status --brief` printing NEXT; the numbered path `eccode quick` prints; `handoff draft`.
- Self-approval refused; the author's evidence cannot support the review; gate order; file ownership; every
  changed file must be reviewed; 30 parallel commits keep the chain intact; a naive edit of the log fails `audit`.
- The engine refuses rather than warns, and quotes its reason.

## 6. Honest limits of this review
- Not covered: the MCP server, the greenfield engine (`eccode-gf`), memory, the Lab, and a real run on Windows.
- The effect of the four fixes on a weak model is not measured; the pilot has not been re-run.
- Turn and dispatch counts for real runs are estimates from a hand-driven session, not from model runs.
- Even with every item done, ECCode adds steps. Whether a weak model with ECCode beats a strong model alone on
  cost is an open question that only P5 can answer.
